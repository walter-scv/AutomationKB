En el capítulo anterior viste que una operación asíncrona puede tardar en
responder. También puede fallar directamente — un servidor que no
contesta, un dato con un formato inesperado. Esta es la última pieza de
programación de esta guía: qué hacer cuando algo falla.

## Conceptos

`try { ... } catch (error) { ... }` permite capturar un fallo sin que el
programa entero se detenga. El bloque `try` contiene el código que puede
fallar; si falla, el control salta directo al bloque `catch`:

```ts
try {
  const datos = await obtenerDatos();
  console.log(datos);
} catch (error) {
  console.log('No se pudo obtener los datos:', error);
}
```

Si `obtenerDatos()` falla, el programa no se corta: entra al `catch`, que
deja constancia de qué pasó, y después sigue con la línea siguiente al
`try/catch`.

Un caso típico es `JSON.parse`, que convierte texto JSON en un valor y lanza
un error si el texto no tiene el formato esperado:

```ts
try {
  const configuracion = JSON.parse(texto);
  aplicar(configuracion);
} catch (error) {
  console.warn('Configuración inválida:', error);
}
```

### Leer un error

Un error no capturado detiene el programa y deja en la consola dos datos:
el **mensaje**, que dice qué pasó, y la **traza** (*stack trace*), que dice
dónde pasó:

```text
TypeError: Cannot read properties of undefined (reading 'precio')
    at calcularSubtotal (src/carrito/subtotal.ts:14:28)
    at confirmarCompra (src/checkout/confirmar.ts:42:17)
    at HTMLButtonElement.onClick (src/checkout/boton.ts:8:5)
```

La primera línea tiene el tipo de error (`TypeError`) y el mensaje: se
intentó leer `precio` de algo que era `undefined`. Las líneas que empiezan
con `at` son la traza, de la más reciente a la más antigua: el error
ocurrió en la función `calcularSubtotal`, en la línea 14, columna 28 del
archivo `subtotal.ts`; esa función la llamó `confirmarCompra`, y a esta, el
clic en un botón. Leída de abajo hacia arriba, la traza cuenta el camino
que llevó al error. Para un reporte de defecto es información de primer
nivel: le dice a quien debuggea exactamente por dónde empezar.

### El error dentro del `catch`

Como cualquier cosa se puede lanzar con `throw`, TypeScript no sabe de
antemano qué llega al `catch`, y lo trata como `unknown`. Para usar sus
propiedades, primero hay que confirmar que es un `Error`:

```ts
try {
  await cargarPerfil();
} catch (error) {
  if (error instanceof Error) {
    console.error('Falló la carga del perfil:', error.message);
  } else {
    console.error('Falló la carga del perfil:', error);
  }
}
```

`error.message` es el texto del error, y `error.name` su tipo
(`TypeError`, `Error`, etc.). Pasar el error completo a `console.error`,
como en los ejemplos anteriores, muestra además la traza.

### El error es un objeto

El parámetro del `catch` es el error que se produjo. Incluirlo en el mensaje
permite diagnosticar después:

```ts
try {
  await cargarPerfil();
} catch (error) {
  console.error('Falló la carga del perfil:', error);
}
```

Un mensaje fijo como `'Algo salió mal'` no dice qué pasó. El error real
tiene la información que hace falta para investigar.

### `throw`: lanzar un error

Además de los errores que produce el sistema, el código puede lanzar uno
propio con `throw`:

```ts
if (!respuesta.ok) {
  throw new Error('HTTP ' + respuesta.status);
}
```

`throw` corta el flujo en ese punto y propaga el error hacia arriba. Si
nadie lo captura, el programa termina con ese error.

Dentro de un `catch`, `throw error` vuelve a lanzar el mismo error para que
lo maneje quien llamó:

```ts
try {
  await sincronizarPedidos();
} catch (error) {
  console.error('No se pudo sincronizar:', error);
  throw error;
}
```

En cambio, crear un error nuevo sin incluir el original pierde la causa:

```ts
try {
  await sincronizarPedidos();
} catch (error) {
  throw new Error('No se pudo sincronizar');
}
```

Si hace falta agregar contexto, hay que conservar la información del error
original:

```ts
throw new Error('No se pudo sincronizar: ' + String(error));
```

Para agregar contexto sin perder la información original, `Error` acepta
una opción `cause` que conserva el error que lo provocó:

```ts
try {
  await sincronizarInventario();
} catch (error) {
  throw new Error('No se pudo sincronizar el inventario', {cause: error});
}
```

Quien reciba el error nuevo tiene el mensaje con contexto y, en
`error.cause`, el error original con su mensaje y su traza.

### Un `catch` que no maneja nada

Un `catch` vacío, o uno que solo muestra un mensaje y sigue, deja el
programa como si no hubiera fallado:

```ts
try {
  await enviarFactura(pedido);
} catch {
  console.log('Seguimos');
}
```

El problema real queda oculto. Peor todavía es devolver un resultado exitoso
desde el `catch`:

```ts
async function actualizar(usuario: Usuario): Promise<boolean> {
  try {
    await actualizarPerfil(usuario);
  } catch {
    return true; // miente: la actualización falló
  }
  return true;
}
```

Quien llama recibe `true` y cree que todo salió bien. Si la operación falló,
el resultado tiene que reflejarlo: devolver `false`, relanzar el error o
devolver un valor que distinga el fallo.

### El `try` tiene que abarcar lo justo

Un `try` demasiado grande mezcla operaciones con causas distintas:

```ts
try {
  const usuario = await obtenerUsuario(id);
  const pedidos = await obtenerPedidos(id);
  const resumen = calcularResumen(pedidos);
  await guardarResumen(usuario.id, resumen);
} catch (error) {
  console.log('Error en el proceso:', error);
}
```

Si algo falla, el mensaje no dice si fue el usuario, los pedidos o el
guardado. Conviene envolver solo la operación que puede fallar y darle un
mensaje específico, o separar las operaciones riesgosas en sus propios
`try/catch`.

También sobra envolver código que no puede fallar:

```ts
try {
  const nombreNormalizado = nombre.trim().toLowerCase();
} catch (error) {
  console.log('Error al normalizar el nombre:', error);
}
```

`trim` y `toLowerCase` sobre un `string` no fallan por un motivo externo.
El `try` no protege de nada y hace parecer que hay un riesgo que no existe.

### `finally`

`finally` se ejecuta siempre, haya error o no. Sirve para limpiar recursos:

```ts
try {
  await procesarArchivo();
} catch (error) {
  console.error('Falló el procesamiento:', error);
} finally {
  await cerrarArchivo();
}
```

"Siempre" incluye el caso en el que el `catch` vuelve a lanzar el error con
`throw`: primero se ejecuta el `finally`, y recién después el error sigue
viaje hacia quien llamó a la función. Por eso es el lugar para cerrar o
liberar algo, pase lo que pase.

### Errores con `await`

En una operación asíncrona, el `try/catch` solo atrapa el rechazo si se
espera la Promise con `await`:

```ts
try {
  guardarPedido(pedido); // falta await: el catch no atrapa el rechazo
} catch (error) {
  console.error('Falló el guardado:', error);
}
```

Sin `await`, la función sigue y el rechazo queda sin manejar. La versión
correcta espera la operación:

```ts
try {
  await guardarPedido(pedido);
} catch (error) {
  console.error('Falló el guardado:', error);
}
```

## Cuándo usarlo

Alrededor de operaciones que pueden fallar por un motivo externo y
esperable: una conexión de red, un servidor que no responde, un dato con
un formato inesperado. No alrededor de cualquier línea de código "por las
dudas" — eso dificulta encontrar dónde está el problema real cuando algo
falla de verdad.

## Buenas prácticas

- Envolver en `try`/`catch` específicamente la operación que puede fallar.
- Hacer algo con el error en el `catch`.
- Incluir el error real en el mensaje que se registra.
- No envolver código que no puede fallar.
- Separar operaciones riesgosas sin relación en sus propios try/catch.

## Anti-patrones

- **Un `catch` vacío**.
- **Un comentario en vez de manejo real**.
- **Un mensaje genérico que descarta el error real**.
- **Un `try` que agrupa varias operaciones sin relación**.
- **Envolver en try/catch código que nunca puede fallar**.
