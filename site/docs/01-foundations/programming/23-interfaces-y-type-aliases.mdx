## Conceptos

Cuando un objeto con una forma particular se usa en más de un lugar,
conviene nombrar esa forma con una **interface**. Así TypeScript puede
avisar si falta una propiedad o si alguna tiene el tipo equivocado:

```ts
interface DatosDeRegistro {
  email: string;
  contraseña: string;
  checkboxTildado: boolean;
}

function registrar(datos: DatosDeRegistro): boolean {
  return datos.checkboxTildado && datos.contraseña.length >= 8;
}
```

El parámetro `datos` ya no es un objeto cualquiera: tiene que cumplir la
forma de `DatosDeRegistro`. Si se llama a `registrar` sin `email`, o con
`checkboxTildado` como texto, TypeScript marca el error antes de ejecutar.

La interface también se puede usar para una lista de objetos:

```ts
const registros: DatosDeRegistro[] = [
  {email: 'ana@mail.com', contraseña: 'Abcd1234!', checkboxTildado: true},
];
```

### No repetir la misma forma

Sin un nombre, la misma forma se repite en cada función y en cada variable:

```ts
function registrar(datos: {email: string; contraseña: string; checkboxTildado: boolean}) {
  // ...
}

function validar(datos: {email: string; contraseña: string; checkboxTildado: boolean}) {
  // ...
}
```

Si mañana se agrega un campo, hay que acordarse de cambiar todas las copias.
Con una interface, se cambia en un solo lugar y TypeScript avisa en los
lugares que dejaron de cumplirla.

### Propiedades opcionales

El signo `?` indica que una propiedad puede no estar:

```ts
interface Usuario {
  email: string;
  telefono?: string;
}

const usuario: Usuario = {email: 'ana@mail.com'}; // válido
```

Al leer una propiedad opcional, el valor puede ser `undefined`, así que hay
que confirmarlo antes de usarlo. No conviene marcar todo como opcional "por
las dudas": si un dato es obligatorio para que la operación funcione, tiene
que ser obligatorio en el tipo.

```ts
interface DatosDeRegistro {
  email?: string;
  contraseña?: string;
  checkboxTildado?: boolean;
}
```

Con esa interface, TypeScript obliga a preguntar por cada propiedad antes de
usarla; se pierde la garantía de que los datos necesarios están.

### Type alias

Un **type alias** le pone nombre a un tipo. Es especialmente útil para un
conjunto cerrado de valores posibles:

```ts
type EstadoDeCuenta = 'sin verificar' | 'verificada' | 'bloqueada';

let estado: EstadoDeCuenta = 'verificada'; // válido
estado = 'otro';                           // Error: no es un estado permitido
```

También puede nombrar la forma de un objeto:

```ts
type DatosDeRegistro = {
  email: string;
  contraseña: string;
  checkboxTildado: boolean;
};
```

Para objetos, `interface` y `type` hacen casi lo mismo. `interface` es la
forma más común cuando la intención es describir una entidad; `type` es más
flexible para uniones y otros tipos que no son objetos. Lo importante es
elegir uno y usarlo de forma consistente.

### Lo que TypeScript informa cuando un objeto no cumple su tipo

Declarar una interface es útil por los errores que permite detectar. Con
esta interface:

```ts
interface Producto {
  codigo: string;
  precio: number;
  stock: number;
}
```

TypeScript marca tres situaciones distintas. Si falta una propiedad
obligatoria:

```ts
const teclado: Producto = {codigo: 'TEC-01', precio: 15000};
```

```text
error TS2741: Property 'stock' is missing in type '{ codigo: string; precio: number; }'
but required in type 'Producto'.
```

Si una propiedad tiene el tipo equivocado:

```ts
const teclado: Producto = {codigo: 'TEC-01', precio: '15000', stock: 4};
```

```text
error TS2322: Type 'string' is not assignable to type 'number'.
```

Y si se agrega una propiedad que la interface no declara, muchas veces por
un error de tipeo:

```ts
const teclado: Producto = {codigo: 'TEC-01', precio: 15000, stok: 4};
```

```text
error TS2353: Object literal may only specify known properties,
and 'stok' does not exist in type 'Producto'.
```

En los tres casos el mensaje nombra la propiedad y el tipo involucrados.
Sin la interface, los tres errores pasarían sin aviso y aparecerían al
ejecutar, probablemente lejos de donde se cometieron.

### Usar una propiedad opcional

Una propiedad opcional puede valer `undefined`, y TypeScript obliga a
contemplarlo antes de usarla como si siempre existiera:

```ts
interface Contacto {
  email: string;
  telefono?: string;
}

function formatearTelefono(contacto: Contacto): string {
  return contacto.telefono.replace('-', '');
}
```

```text
error TS18048: 'contacto.telefono' is possibly 'undefined'.
```

La solución es comprobarlo primero. Después de la comprobación, TypeScript
sabe que en esa rama el valor existe:

```ts
function formatearTelefono(contacto: Contacto): string {
  if (contacto.telefono === undefined) {
    return 'Sin teléfono';
  }
  return contacto.telefono.replace('-', '');
}
```

Este chequeo es la razón por la que no conviene marcar propiedades como
opcionales "por las dudas": cada propiedad opcional obliga a tratar su
ausencia en cada lugar donde se usa.

### Union types: un valor que puede ser de más de un tipo

El `|` del type alias `EstadoDeCuenta` no es exclusivo de los textos fijos.
Un **union type** declara que un valor puede ser de cualquiera de varios
tipos. Es lo que pasa con un dato que llega de distintas fuentes, o con un
valor que puede faltar:

```ts
let codigoDeBarras: string | number;   // a veces llega como texto, a veces como número
let fechaDeBaja: Date | null;          // null mientras la cuenta está activa
```

Sobre un valor así, TypeScript solo permite lo que es válido para **todos**
los tipos de la unión:

```ts
function normalizarCodigo(codigo: string | number): string {
  return codigo.toUpperCase();
}
```

```text
error TS2339: Property 'toUpperCase' does not exist on type 'string | number'.
  Property 'toUpperCase' does not exist on type 'number'.
```

La segunda línea del mensaje dice cuál de los tipos es el problema: un
`number` no tiene `toUpperCase`. Para usar el método hay que averiguar
primero cuál de los dos tipos es.

### Narrowing: averiguar cuál de los tipos es

Comprobar el tipo dentro de un `if` hace que TypeScript **acote**
(*narrowing*) el tipo en esa rama, igual que pasó con la propiedad opcional
y `undefined`. La comprobación depende de qué se quiere distinguir.

Para tipos básicos se usa `typeof`, que devuelve el nombre del tipo como
texto (`'string'`, `'number'`, `'boolean'`):

```ts
function normalizarCodigo(codigo: string | number): string {
  if (typeof codigo === 'number') {
    return String(codigo);        // acá codigo es number
  }
  return codigo.toUpperCase();    // acá solo puede ser string
}
```

Para un valor que puede ser `null` o `undefined`, se compara directamente.
Sin esa comprobación, usar `fechaDeBaja.toLocaleDateString()` da
`error TS18047: 'fechaDeBaja' is possibly 'null'`, el equivalente para
`null` del error que se vio con la propiedad opcional:

```ts
function textoDeBaja(fechaDeBaja: Date | null): string {
  if (fechaDeBaja === null) {
    return 'Cuenta activa';
  }
  return `Baja: ${fechaDeBaja.toLocaleDateString()}`;
}
```

Para distinguir un array de un valor suelto, `typeof` no sirve (un array
da `'object'`); se usa `Array.isArray`:

```ts
function cantidadDeDestinatarios(para: string | string[]): number {
  if (Array.isArray(para)) {
    return para.length;           // acá es string[]
  }
  return 1;                       // un solo email
}
```

### Uniones de objetos con una propiedad que las distingue

El caso más útil es una unión de objetos que comparten una propiedad con
un valor fijo distinto en cada uno. Esa propiedad (el *discriminante*)
indica cuál de las formas es, y con ella TypeScript sabe qué otras
propiedades existen:

```ts
type ResultadoDePago =
  | { estado: 'aprobado'; comprobante: string }
  | { estado: 'rechazado'; motivo: string };

function mensajeDePago(resultado: ResultadoDePago): string {
  if (resultado.estado === 'aprobado') {
    return `Pago aprobado. Comprobante ${resultado.comprobante}`;
  }
  return `Pago rechazado: ${resultado.motivo}`;
}
```

Sin comprobar `estado`, `resultado.motivo` da error, porque un pago
aprobado no tiene motivo:

```text
error TS2339: Property 'motivo' does not exist on type 'ResultadoDePago'.
  Property 'motivo' does not exist on type '{ estado: "aprobado"; comprobante: string; }'.
```

Así se modelan respuestas que tienen formas distintas según el resultado,
y el compilador impide leer un dato que en ese caso no existe.

Para quien prueba, un union type es una lista explícita de casos: cada
tipo de la unión es un camino distinto del código. `normalizarCodigo` se
prueba con un string y con un número; `textoDeBaja`, con una fecha y con
`null`; `mensajeDePago`, con un pago aprobado y con uno rechazado.

### Reutilizar una forma con `extends`

Cuando una entidad tiene todas las propiedades de otra y algunas más, una
interface puede **extender** a otra en lugar de repetirlas:

```ts
interface Persona {
  nombre: string;
  email: string;
}

interface Empleado extends Persona {
  legajo: number;
  area: string;
}

const empleada: Empleado = {nombre: 'Ana', email: 'ana@empresa.com', legajo: 1042, area: 'QA'};
```

`Empleado` tiene las cuatro propiedades. Si mañana `Persona` suma un
teléfono, `Empleado` lo hereda sin cambios.

### Nombres de tipos

El nombre del tipo también comunica: `DatosDeRegistro`, `EstadoDeCuenta`,
`Pedido`. `Tipo1` o `Datos` no dicen qué representa la forma y obligan a
leer todas las propiedades para descubrirlo.

### `any` no reemplaza un tipo

Declarar el parámetro como `any` hace que TypeScript no revise nada:

```ts
function registrar(datos: any): boolean {
  return datos.checkboxTildado && datos.contraseña.length >= 8;
}
```

La función compila aunque `datos` no tenga `contraseña`; el error aparece en
ejecución. Una interface mantiene el chequeo y documenta qué forma se
espera.

## Cuándo usarlo

Declarar una interface o un type alias vale la pena cuando la misma forma
de objeto se repite en más de una función, o cuando un valor solo puede
ser uno de un conjunto cerrado de opciones. Para un parámetro de un solo
valor simple (`string`, `number`, `boolean`), alcanza con el tipo simple —
no hace falta nombrar nada extra.

## Buenas prácticas

- Declarar una interface en cuanto la misma forma de objeto se usa en más de un lugar.
- Usar un type alias para limitar un valor a un conjunto cerrado de opciones válidas.
- Elegir un nombre que diga qué entidad representa.
- Marcar `?` (opcional) solo en propiedades que de verdad pueden faltar.
- Acotar un union type con `typeof`, una comparación, `Array.isArray` o su discriminante antes de usarlo.
- Nunca usar `any` para "resolver" un error de tipos.

## Anti-patrones

- **Parámetro sin tipo declarado**.
- **Repetir la misma forma de objeto**.
- **Nombre de tipo genérico**.
- **Todas las propiedades marcadas opcionales "por las dudas"**.
- **Usar `any` para que TypeScript "deje de molestar"**.
- **Probar un solo tipo de un union type** y dar por cubiertos los demás.
