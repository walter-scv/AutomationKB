Las técnicas anteriores (equivalence partitioning, boundary value analysis,
decision tables) asumen que el resultado depende solo de los datos de
entrada. Pero a veces el resultado depende también de **en qué estado
está el sistema** — y ahí esas técnicas no alcanzan.

## Conceptos

Las técnicas anteriores asumen que, ante los mismos datos, el sistema
responde siempre igual. Muchos sistemas no funcionan así: la misma acción
es válida o inválida según lo que pasó antes. Una tarjeta permite comprar
si está activa y lo rechaza si está bloqueada, aunque el monto y el
comercio sean idénticos. Cuando el comportamiento depende de la historia
del sistema, la técnica que corresponde es **state transition testing**.

### El modelo: estados, eventos y transiciones

La técnica parte de un modelo del sistema con tres elementos. Los
**estados** son las situaciones en las que puede estar. Los **eventos**
son lo que ocurre y puede provocar un cambio. Las **transiciones** son los
cambios de un estado a otro que un evento provoca. Una transición puede
tener además una **condición** que debe cumplirse para que ocurra y una
**acción** que el sistema realiza al pasar. La notación habitual de una
transición es `evento [condición] / acción`.

Una tarjeta de débito, con estas reglas de negocio:

> La tarjeta se emite inactiva y se activa con el PIN correcto. Tres PIN
> incorrectos seguidos la bloquean, y se envía un SMS al titular. Desde el
> bloqueo, se desbloquea validando la identidad en el home banking. Activa
> o bloqueada, se puede dar de baja; una tarjeta dada de baja ya no puede
> volver a usarse.

produce este modelo, con una transición por línea:

```text
Emitida    ── ingresar PIN [PIN correcto] ─────────────▶  Activa
Activa     ── ingresar PIN [3.er PIN incorrecto] / enviar SMS ──▶  Bloqueada
Bloqueada  ── validar identidad ───────────────────────▶  Activa
Activa     ── dar de baja ─────────────────────────────▶  Dada de baja
Bloqueada  ── dar de baja ─────────────────────────────▶  Dada de baja
```

Y la misma información en una **tabla de estados**, que tiene una ventaja
sobre el diagrama: muestra explícitamente las transiciones inválidas, que
son las celdas vacías.

| Estado \ Evento | PIN correcto | 3.er PIN incorrecto | Validar identidad | Dar de baja |
|---|---|---|---|---|
| Emitida | Activa | | | |
| Activa | | Bloqueada / SMS | | Dada de baja |
| Bloqueada | | | Activa | Dada de baja |
| Dada de baja | | | | |

Cada celda vacía es una combinación de estado y evento que el sistema
tiene que rechazar: validar identidad sobre una tarjeta activa, activar
una tarjeta bloqueada con el PIN o hacer cualquier cosa con una tarjeta
dada de baja. Dada de baja es un **estado final**: no tiene transiciones
de salida.

### Casos de prueba como secuencias de eventos

Un caso de prueba en esta técnica es una secuencia de eventos que lleva al
sistema por una serie de estados. Un solo caso suele cubrir varias
transiciones:

```text
CT-01  Emitida → [PIN correcto] → Activa → [3.er PIN incorrecto] → Bloqueada
       → [validar identidad] → Activa → [dar de baja] → Dada de baja
       Verificar en cada paso: el estado que muestra el home banking y,
       al bloquear, que llegue el SMS.
```

### Criterios de cobertura

Cuánto probar se define con un criterio de cobertura. Hay tres
habituales, de menor a mayor exigencia.

La cobertura de **todos los estados** pide que cada estado se visite al
menos una vez. CT-01 la logra sola: pasa por los cuatro estados. Es el
criterio más débil, porque se puede cumplir sin probar todas las
transiciones; CT-01 nunca prueba dar de baja una tarjeta bloqueada.

La cobertura de **transiciones válidas** pide que cada transición válida
se ejecute al menos una vez. La tarjeta tiene cinco: activar, bloquear,
desbloquear, dar de baja desde activa y dar de baja desde bloqueada. CT-01
cubre cuatro; hace falta un segundo caso que llegue a Bloqueada y dé de
baja desde ahí. Es el criterio más usado, y cumplirlo garantiza también
la cobertura de todos los estados.

La cobertura de **todas las transiciones** suma, a las válidas, el intento
de cada transición inválida de la tabla: las celdas vacías. La tabla tiene
16 celdas, 5 válidas y 11 inválidas, así que este criterio pide intentar
las 11 inválidas y comprobar que cada una se rechaza. Es el criterio
mínimo recomendado para sistemas críticos.

Al probar transiciones inválidas conviene **intentar una sola por caso**.
Si un caso intenta dos y la primera no se rechaza como debía, el sistema
queda en un estado inesperado y el resultado de la segunda deja de
significar algo: un defecto oculta al otro, lo que se conoce como
enmascaramiento de defectos.

### Definir qué significa "rechazar"

Para cada transición inválida, el caso tiene que decir qué se espera
exactamente. Un sistema puede impedir una transición de dos maneras: no
ofreciendo la opción (el botón «Activar» no aparece en una tarjeta dada
de baja) o rechazándola con un mensaje (el servicio responde «La tarjeta
fue dada de baja»). Son dos comportamientos distintos, y si el caso no
especifica cuál se espera, dos personas pueden dar por buena la misma
pantalla con interpretaciones opuestas.

## Cuándo usarlo

State transition testing conviene cuando el comportamiento depende del
estado en que se encuentra algo: cuentas, pedidos, suscripciones, flujos
de aprobación, sesiones de usuario, cualquier entidad con un ciclo de
vida. Una señal clara de que hace falta es encontrar en el requisito
frases como "solo si está…", "una vez que…" o "ya no puede…".

## Buenas prácticas

- Armar el modelo a partir del requisito y confirmarlo con quien lo
  definió antes de diseñar casos.
- Usar la tabla de estados para no pasar por alto las transiciones
  inválidas.
- Cubrir como mínimo todas las transiciones válidas.
- Intentar una sola transición inválida por caso.
- Especificar, para cada transición inválida, cómo se manifiesta el
  rechazo.

## Anti-patrones

- **Probar solo el camino principal**, sin ramas alternativas ni
  transiciones inválidas.
- **Suponer transiciones que el modelo no tiene** porque "parecen
  lógicas".
- **Dejar ambiguo qué se espera ante una transición inválida**.
- **Juntar varias transiciones inválidas en un mismo caso**.
