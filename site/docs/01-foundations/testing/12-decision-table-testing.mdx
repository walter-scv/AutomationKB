## Conceptos

Ya sabés elegir buenos valores para un campo (equivalence partitioning y
boundary value analysis). Pero un formulario no tiene un campo solo —
tiene varios, y a veces el resultado depende de cómo se **combinan** entre
sí, no de cada uno por separado. Equivalence partitioning no cubre esto:
trata cada campo de forma aislada.

**Decision table testing** enumera las combinaciones relevantes entre dos
o más condiciones, y el resultado esperado para cada una. Para el
formulario de registro, combinando la validez de la contraseña con el
estado del checkbox de términos:

| Contraseña válida | Checkbox tildado | Resultado |
|---|---|---|
| Sí | Sí | Crea la cuenta |
| Sí | No | No crea la cuenta |
| No | Sí | No crea la cuenta |
| No | No | No crea la cuenta |

Si solo se probara cada campo por separado, se podría dejar sin cubrir la
combinación "contraseña válida + checkbox destildado" — una combinación
real que un usuario puede encontrar, y que equivalence partitioning, al
mirar cada campo de forma aislada, no obliga a probar.

## Cuándo usarlo

Decision table testing aplica cuando dos o más condiciones **interactúan**
en la lógica de negocio: el resultado cambia según cómo se combinen, no
solo según el valor de una sola. Si dos campos son independientes entre sí
(ninguno afecta el resultado del otro), combinar sus valores en una tabla
no agrega cobertura real — ahí alcanza con equivalence partitioning sobre
cada uno por separado.

## Buenas prácticas

- **Identificar primero qué condiciones realmente interactúan** en la
  lógica de negocio, antes de armar la tabla. Si no está claro, conviene
  preguntarse: "¿cambiar el valor de esta condición cambia el resultado
  cuando la otra ya está fija?" — si la respuesta es no, no interactúan.
- **Incluir solo esas condiciones.** Combinar campos que no interactúan
  infla la tabla sin agregar cobertura real: con 2 condiciones hay 4
  combinaciones posibles, pero con 4 condiciones independientes ya son
  16 — la mayoría, ruido.
- **Reducir combinaciones imposibles o sin sentido en el dominio**, pero
  marcándolas explícitamente en vez de omitirlas en silencio — así quien
  lea la tabla después sabe que se excluyeron a propósito, no que se
  olvidaron.
- **Revisar la tabla cuando se agregue una condición nueva al
  formulario.** Cada condición nueva puede duplicar el tamaño de la
  tabla — vale la pena confirmar si sigue siendo manejable o si conviene
  dividirla en tablas más chicas.
- **Nombrar cada fila con la combinación que representa**, no solo con un
  número — "contraseña inválida + checkbox tildado" se entiende sin mirar
  el resto de la tabla; "fila 3" no.

## Anti-patrones

- **Armar una decision table para campos independientes** que no
  interactúan entre sí — es trabajo de más; equivalence partitioning
  alcanza.
- **Dejar afuera una combinación relevante** por apurarse a completar la
  tabla, dejando sin cubrir justo el caso que un usuario real puede
  encontrar.
- **Repetir una combinación ya cubierta** con datos distintos pero el
  mismo patrón de condiciones — no agrega una fila nueva a la tabla.
- **Armar una tabla gigante combinando todas las condiciones del
  formulario**, sin filtrar primero cuáles interactúan de verdad — el
  número de filas crece exponencialmente, y la mayoría termina siendo
  ruido que nadie revisa en serio.
- **Dejar implícito qué pasa con una combinación inválida en el dominio**
  (como "edad negativa + cuenta premium"), en vez de decidir y documentar
  explícitamente el resultado esperado ahí.
