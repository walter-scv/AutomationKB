## Conceptos

Las técnicas de caja negra vistas hasta acá derivan los casos de una
especificación. Pero las especificaciones nunca anticipan todo, a veces
están incompletas y no siempre hay tiempo para aplicar una técnica formal
a cada funcionalidad. Las **técnicas basadas en la experiencia** usan el
conocimiento de quien prueba (cómo falló el sistema antes, qué errores
suele cometer un equipo, qué falla en aplicaciones parecidas) para
encontrar defectos que las técnicas sistemáticas no buscan. Las tres
principales son error guessing, testing exploratorio y testing basado en
checklists.

Los ejemplos de esta lección usan la misma funcionalidad: la carga de
documentos adjuntos en un trámite online, que acepta archivos PDF o JPG de
hasta 5 MB.

### Error guessing

**Error guessing** consiste en anticipar dónde es probable que haya
errores, defectos o fallos, y diseñar pruebas específicamente para esas
sospechas. Se apoya en cómo funcionó la aplicación en el pasado, en los
tipos de error que tienden a cometer los desarrolladores y en los fallos
vistos en aplicaciones similares.

Para no depender solo de la memoria, conviene recorrer las categorías en
las que suelen aparecer los problemas. Aplicadas a la carga de
documentos:

- **Entrada:** un archivo de 0 bytes; uno de exactamente 5 MB y otro de
  5,01 MB; la extensión en mayúsculas (`.PDF`); un nombre con tildes,
  espacios o 200 caracteres; un ejecutable renombrado como `.pdf`.
- **Salida:** ¿el nombre del archivo se muestra igual que como se subió,
  o con caracteres extraños?
- **Lógica:** subir el mismo archivo dos veces; eliminar un adjunto y
  volver a subirlo; enviar el trámite sin ningún adjunto.
- **Interfaces:** cortar la conexión a mitad de la carga; subir desde el
  celular con la cámara en lugar de un archivo.
- **Datos:** ¿qué queda guardado si la carga se interrumpe: un archivo
  incompleto, o nada?

Cuando esta lista se arma de forma deliberada y se usa para diseñar
pruebas que provoquen esos fallos, se la llama **ataque de fallos**
(*fault attack*). Las listas más útiles salen del historial real: si en
el último año hubo tres incidentes con nombres de archivo con tildes en
este sistema, esa prueba va primero. La experiencia sirve para saber
dónde mirar, no para dar por hecho qué va a fallar: los defectos típicos
de una tienda online no tienen por qué repetirse en un sistema de
trámites.

### Testing exploratorio

En el **testing exploratorio**, las pruebas se diseñan, se ejecutan y se
evalúan al mismo tiempo, mientras quien prueba aprende sobre el sistema:
lo que se observa en una prueba decide la siguiente. No es probar sin
criterio. Para que tenga dirección y se pueda evaluar, se organiza en
**sesiones**, cada una con un tiempo definido (*timebox*) y un **charter**
que fija el objetivo:

```text
Charter:   Explorar la carga de adjuntos con archivos límite y conexiones
           inestables, para encontrar casos en que el trámite quede con
           documentos incompletos.
Timebox:   60 minutos
```

Durante la sesión se registra lo que se hace y lo que se encuentra, en una
hoja de sesión:

```text
Hoja de sesión — 12/11, 10:00 a 11:00
10:05  PDF de 4,9 MB: se carga bien.
10:12  PDF de 5,2 MB: mensaje «El archivo supera el máximo». OK.
10:20  Corto el wifi al 50% de un PDF de 4 MB: la barra queda detenida,
       sin mensaje. Al volver la conexión, el adjunto figura como cargado.
       → Descargarlo: el archivo está incompleto (2 MB). DEF-501.
10:38  Siguiendo lo anterior: cierro la pestaña a mitad de carga. Mismo
       resultado: queda un adjunto incompleto. Se agrega a DEF-501.
10:50  Ideas para otra sesión: cargas en paralelo de varios archivos.
```

La sesión termina con un **debriefing**: una conversación breve con quien
necesita los resultados, en la que se repasa qué se cubrió, qué se
encontró y qué conviene explorar después. Registrar a medida que se
avanza no es un detalle: sin casos escritos de antemano, la hoja de sesión
es la única evidencia de qué se probó.

El testing exploratorio rinde especialmente cuando la especificación es
escasa, cuando hay poco tiempo y como complemento de las técnicas
formales. Dentro de una sesión se pueden usar otras técnicas: el PDF de
4,9 MB y el de 5,2 MB son, en el fondo, un boundary value analysis
improvisado.

### Testing basado en checklists

En el **testing basado en checklists**, las pruebas se diseñan y ejecutan
para cubrir una lista de condiciones de alto nivel. A diferencia de un
caso de prueba, cada ítem dice **qué revisar**, no con qué datos ni qué
resultado exacto esperar. Los ítems se suelen escribir como preguntas, y
cada uno tiene que poder comprobarse por separado y de forma directa:

```text
Checklist — Carga de archivos
¿Se rechaza un archivo con un formato no permitido, con un mensaje que indica los permitidos?
¿Se rechaza un archivo que supera el tamaño máximo, indicando cuál es el máximo?
¿Se puede eliminar un adjunto antes de enviar?
¿Si la carga se interrumpe, el adjunto queda descartado y no como cargado?
¿El nombre del archivo se muestra igual que como se subió?
```

Una checklist útil no incluye ítems demasiado generales ("¿funciona bien
la carga?"), ni cosas que se pueden verificar automáticamente, ni
condiciones que en realidad son criterios para empezar o terminar el
testing. Y se mantiene viva: el cuarto ítem se agregó después de DEF-501,
y los ítems que ya nunca encuentran nada, porque el equipo aprendió a
evitar ese error, se pueden retirar, cuidando que la lista no crezca sin
control. Una checklist armada con los defectos reales del propio sistema
es mucho más efectiva que una lista genérica copiada de otro proyecto.

Como los ítems son de alto nivel, dos personas pueden ejecutar la misma
checklist de formas algo distintas: eso puede ampliar la cobertura, pero
reduce la repetibilidad. Por eso una checklist da consistencia cuando no
hay casos detallados, pero no reemplaza a un caso formal donde hace falta
un resultado exacto.

### Cómo se combinan con las técnicas formales

Las técnicas basadas en la experiencia complementan a las formales; no las
reemplazan. En la carga de documentos, los casos de boundary value
analysis sobre el tamaño máximo confirman la regla especificada; el error
guessing y la sesión exploratoria encontraron el adjunto incompleto, que
ninguna regla mencionaba. En un sistema crítico, depender solo de la
experiencia de una persona deja sin cubrir sus puntos ciegos: la
cobertura formal es el respaldo.

## Cuándo usarlo

Estas técnicas rinden más cuando quien prueba conoce el dominio o el tipo
de sistema, cuando falta tiempo o documentación para diseñar casos
formales y como complemento de la cobertura formal, para encontrar lo que
la especificación no anticipó.

## Buenas prácticas

- Armar las listas de error guessing y las checklists a partir de los
  defectos reales del sistema.
- Dar a cada sesión exploratoria un charter y un timebox.
- Registrar los hallazgos durante la sesión, no al final.
- Revisar periódicamente las checklists: agregar lo nuevo y retirar lo
  que ya no aporta.

## Anti-patrones

- **Depender solo de técnicas basadas en experiencia** en un sistema
  crítico.
- **No documentar el testing exploratorio**.
- **Confundir una checklist con un caso de test formal**.
- **Reemplazar la planificación por exploración sin objetivo ni
  timebox**.
- **Aplicar a ciegas la experiencia de un sistema distinto**.
