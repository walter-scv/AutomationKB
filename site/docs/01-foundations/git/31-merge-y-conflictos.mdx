## Conceptos

Una rama tiene sentido mientras el cambio está en curso. Cuando está
terminado, sus commits tienen que llegar a `main`. Esa integración se hace
con `git merge`, y en la mayoría de los casos Git la resuelve sola. La
excepción son los **conflictos**, que requieren una decisión humana.

### `git merge`

`git merge <rama>` incorpora los commits de esa rama a la rama en la que
se está parado. Para integrar una rama de trabajo a `main`, primero hay
que estar en `main`:

```bash
$ git switch main
$ git merge feature/descuento-por-volumen
```

Según cómo haya evolucionado el historial, el merge termina de una de dos
maneras.

Si `main` no recibió commits nuevos desde que se creó la rama, no hay nada
que combinar: Git simplemente mueve `main` hasta el último commit de la
rama. Esto se llama **fast-forward**:

```text
Antes:
●───●───●              main
         \
          ●───●        feature/descuento-por-volumen

Después:
●───●───●───●───●      main (y la rama, en el mismo commit)
```

```text
Updating 4d5e6f7..7f8e9d0
Fast-forward
 precios.ts | 6 ++++--
 1 file changed, 4 insertions(+), 2 deletions(-)
```

Si `main` también avanzó, porque otras personas integraron cambios
mientras tanto, Git combina las dos líneas y crea un **commit de merge**,
que tiene dos padres:

```text
Antes:
●───●───●───●          main
         \
          ●───●        feature/descuento-por-volumen

Después:
●───●───●───●───◆      main
         \     /
          ●───●        feature/descuento-por-volumen
```

```text
Merge made by the 'ort' strategy.
 precios.ts | 6 ++++--
 1 file changed, 4 insertions(+), 2 deletions(-)
```

En el historial, ese commit aparece con un mensaje del tipo `Merge branch
'feature/descuento-por-volumen'`.

### Traer `main` a la rama de trabajo

El merge también se usa en el sentido inverso. Si una rama lleva varios
días abierta, conviene incorporarle periódicamente lo que se sumó a
`main`, estando en la rama:

```bash
$ git switch feature/descuento-por-volumen
$ git merge main
```

Así los conflictos aparecen de a poco, cuando son chicos y todavía se
recuerda el contexto, en lugar de acumularse para el día de la
integración final.

### Qué es un conflicto

Un conflicto ocurre cuando las dos ramas modificaron **las mismas líneas**
de un archivo de maneras distintas, y Git no puede decidir cuál de las dos
versiones conservar. Si los cambios están en archivos distintos, o en
partes distintas del mismo archivo, Git los combina sin intervención.

```bash
$ git merge main
Auto-merging precios.ts
CONFLICT (content): Merge conflict in precios.ts
Automatic merge failed; fix conflicts and then commit the result.
```

El merge queda en pausa. `git status` muestra qué archivos necesitan
resolución:

```bash
$ git status
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
        both modified:   precios.ts
```

Un conflicto no indica que algo esté roto: indica que hay una decisión
pendiente. Git la deja marcada dentro del archivo:

```text
<<<<<<< HEAD
const aplicaDescuento = cantidad >= 10 || esMayorista;
=======
const aplicaDescuento = cantidad >= 12;
>>>>>>> main
```

Entre `<<<<<<< HEAD` y `=======` está la versión de la rama en la que se
está parado; entre `=======` y `>>>>>>> main`, la que llega de la otra
rama. En el ejemplo, la rama de trabajo agregó el descuento para clientes
mayoristas, y en `main` alguien subió la cantidad mínima de 10 a 12
unidades.

### Resolver el conflicto

Resolver es editar el archivo hasta dejar la versión correcta y quitar las
tres marcas. La versión correcta no siempre es una de las dos: cuando
ambos cambios son válidos, es una tercera que los combina. Acá los dos
cambios responden a decisiones de negocio distintas, y la resolución
correcta conserva ambas:

```ts
const aplicaDescuento = cantidad >= 12 || esMayorista;
```

Los editores como Visual Studio Code muestran botones sobre cada
conflicto: **Accept Current Change** conserva la versión de la rama
actual (la de arriba), **Accept Incoming Change** conserva la que llega
(la de abajo) y **Accept Both Changes** pega las dos una debajo de la
otra. Son atajos útiles cuando una de las versiones es claramente la
correcta, pero no reemplazan la lectura: en el ejemplo, aceptar cualquiera
de las dos versiones habría borrado una regla de negocio.

Con el archivo editado, el resto del procedimiento es fijo:

```bash
$ git add precios.ts       # marcar el conflicto como resuelto
$ git commit               # confirmar el merge; Git propone el mensaje
```

Entre editar y confirmar falta un paso que Git no exige y que es
imprescindible: compilar y volver a correr las pruebas. La línea
combinada es código nuevo, que nadie probó, y que puede tener un error de
lógica aunque Git ya no marque ningún conflicto.

Si durante la resolución se prefiere empezar de nuevo, `git merge --abort`
cancela el merge y deja todo como estaba antes de iniciarlo.

## Cuándo usarlo

Se hace un merge cuando el trabajo de una rama está listo para integrarse
a `main`, y también cuando `main` avanzó y la rama de trabajo necesita
ponerse al día. Cuanto más seguido se hace, más chicos son los conflictos.

## Buenas prácticas

- Traer `main` a la rama de trabajo con frecuencia.
- Leer las dos versiones de un conflicto antes de decidir.
- Combinar los cambios cuando ambos son válidos.
- Volver a probar después de resolver un conflicto a mano.
- Avisar al equipo antes de integrar un cambio grande.

## Anti-patrones

- **Dejar una rama sin integrar durante semanas**.
- **Resolver un conflicto eligiendo una versión sin leer la otra**.
- **No volver a probar después de resolver**.
- **Postergar un merge por miedo al conflicto**.
