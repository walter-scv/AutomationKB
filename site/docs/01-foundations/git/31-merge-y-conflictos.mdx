## Conceptos

Ya sabés crear una rama propia para trabajar. En algún momento, ese
trabajo tiene que volver a `main`:

```bash
git checkout main
git merge validar-contraseña
```

`git merge` suma los commits de una rama a la rama en la que estás
parado — en este caso, los commits de `validar-contraseña` se suman a
`main`.

Un **conflicto de merge** aparece cuando dos ramas cambiaron las mismas
líneas de un archivo de formas distintas, y Git no puede decidir solo cuál
versión usar. Marca el conflicto directamente en el archivo:

```
<<<<<<< HEAD
contraseña.length >= 8
=======
contraseña.length >= 10
>>>>>>> validar-contraseña
```

Alguien tiene que elegir (o combinar) qué versión queda, editar el
archivo a mano, y recién ahí confirmar el merge.

## Cuándo usarlo

Un merge hace falta cada vez que el trabajo de una rama está listo para
sumarse a `main` — o cada vez que `main` avanzó y tu rama necesita
ponerse al día con esos cambios.

## Buenas prácticas

- **Mergear seguido:** cada pocos días, no dejar una rama viviendo
  semanas — así, si aparece un conflicto, es chico y fácil de resolver.
- **Entender ambas versiones antes de resolver un conflicto:** leer qué
  hace cada lado, no elegir una al azar — combinar a ciegas puede borrar
  un cambio real de otra persona.
- **Traer los cambios de `main` a la rama propia seguido** (no solo al
  final), para encontrar conflictos chicos de a poco en vez de uno
  gigante al mergear.
- **Volver a probar el código después de resolver un conflicto a mano:**
  una combinación manual puede compilar y aun así tener un error de
  lógica que ningún conflicto marcado iba a avisar.
- **Avisar al equipo antes de mergear algo grande,** para que nadie quede
  trabajando sobre una base que está por cambiar mucho.

## Anti-patrones

- **Dejar una rama sin mergear durante semanas** mientras el resto del
  equipo sigue sumando cambios a `main` — el conflicto, cuando aparezca,
  va a ser mucho más grande.
- **Resolver un conflicto a las apuradas**, eligiendo una versión sin
  entender qué hacía la otra — puede borrar un cambio real de alguien más.
- **Quedarse con una versión sin leer la otra** ("la mía total"), en vez
  de combinar lo que corresponde de cada una.
- **No volver a correr nada después de resolver un conflicto a mano** —
  una combinación mal hecha puede dejar el código roto aunque Git ya no
  marque ningún conflicto pendiente.
- **Posponer un merge por miedo al conflicto** — evitarlo no lo hace
  desaparecer, solo garantiza que sea más grande cuando no quede otra.
