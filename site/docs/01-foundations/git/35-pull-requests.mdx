## Conceptos

Un **Pull Request (PR)** es el pedido, dentro de GitHub, de que el equipo
revise los commits de tu rama antes de sumarlos a `main`. Al abrir un PR,
GitHub muestra el diff completo de los cambios: el equipo puede dejar
comentarios línea por línea, pedir cambios, o aprobarlo.

Cuando se aprueba, se **mergea**: los commits se suman a `main`. GitHub
ofrece tres formas de hacerlo — un merge normal (conserva todos los
commits de la rama tal cual), "squash" (junta todos los commits de la
rama en uno solo) o "rebase" (los aplica de forma lineal, sin un commit de
merge).

## Cuándo usarlo

Un Pull Request se abre cada vez que una rama está lista para sumarse a
`main` y necesita pasar por revisión del equipo antes — prácticamente
siempre que se trabaja en equipo sobre un mismo repositorio.

## Buenas prácticas

- **Mantener el Pull Request chico y enfocado en un solo cambio**: es más
  rápido y más fácil de revisar a fondo, y más fácil de revertir si algo
  sale mal.
- **Escribir una descripción que explique qué cambia y por qué**, para que
  quien revise no tenga que adivinarlo abriendo cada archivo del diff.
- **Responder o resolver cada comentario de revisión**, no ignorarlos ni
  dejarlos "flotando" — un comentario sin cerrar es una duda sin resolver
  sobre el cambio.
- **Actualizar el PR con los últimos cambios de `main` antes de mergear**,
  para evitar integrar sobre una base que ya quedó vieja.
- **Abrir como "draft" un PR que todavía no está listo para revisión**,
  para distinguirlo de uno que sí espera comentarios y aprobación.

## Anti-patrones

- **Un Pull Request enorme que mezcla varios cambios sin relación** —
  quien lo revisa tarda mucho más, y es más probable que algo se le
  escape.
- **Mergear sin que nadie haya revisado ni aprobado** — anula por completo
  el propósito de abrir un Pull Request.
- **Dejar comentarios de revisión sin responder ni resolver**, y mergear
  igual — es como si nunca se hubiera pedido la revisión.
- **Abrir un PR sin descripción**, dejando que quien lo revise reconstruya
  solo, archivo por archivo, qué cambió y por qué.
