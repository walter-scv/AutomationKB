## Conceptos

Hasta acá, integrar una rama a `main` era un `git merge` que hacía la
misma persona que escribió el cambio. En un equipo, antes de que un cambio
llegue a `main`, otra persona lo revisa. El mecanismo para eso en GitHub
es el **Pull Request** (PR): un pedido de que el equipo revise los commits
de una rama antes de integrarlos.

### Abrir un Pull Request

Un PR se abre sobre una rama que ya está en el remoto. Al subirla por
primera vez, la propia salida del push incluye el enlace para crearlo:

```bash
$ git push -u origin fix/email-con-mas
remote: Create a pull request for 'fix/email-con-mas' on GitHub by visiting:
remote:      https://github.com/empresa/tienda/pull/new/fix/email-con-mas
```

También aparece un aviso *Compare & pull request* en la página del
repositorio. En el formulario se eligen dos ramas: **base**, hacia donde
va el cambio (normalmente `main`), y **compare**, la rama con el cambio.
GitHub muestra debajo los commits que se van a integrar y el diff completo.

### Título y descripción

El título sigue la misma regla que un mensaje de commit: dice qué cambia,
empezando con un verbo. "Aceptar emails con + en el registro" informa;
"ajustes" no. Si el título necesita un "y" para describir el PR, contiene
dos cambios, y conviene separarlos: un PR enfocado se revisa más rápido y
con más atención, y se puede revertir sin arrastrar nada más.

La descripción le ahorra a quien revisa reconstruir el cambio archivo por
archivo. Una estructura habitual, escrita en Markdown, cubre qué cambia,
por qué y cómo comprobarlo:

```markdown
## Qué cambia
El registro acepta emails con `+`, como `ana+tienda@mail.com`.

## Por qué
Soporte reportó clientes que no podían registrarse con ese tipo de
dirección: la validación rechazaba cualquier `+` antes de la arroba.

## Cómo probarlo
1. Ir al registro.
2. Completar el email con `ana+tienda@mail.com` y el resto de los datos.
3. La cuenta se crea y aparece «Cuenta creada».

Se agregó un test que cubre el caso.
```

La sección "Cómo probarlo" es especialmente útil para quien testea: indica
con qué datos se verifica el cambio.

### Draft

Si se quiere mostrar el avance pero el cambio todavía no está listo (faltan
pruebas o una parte del desarrollo), el PR se crea como **draft**,
eligiendo *Create draft pull request*. GitHub lo marca como borrador y no
lo presenta como listo para revisar. Cuando está terminado, se indica
*Ready for review* y recién entonces se pide la revisión.

### La revisión

Quien revisa trabaja en la pestaña *Files changed*, donde ve el diff y
puede comentar cualquier línea. Al terminar, deja una de tres respuestas:
**Comment**, para observaciones o preguntas que no aprueban ni bloquean;
**Approve**, si el cambio está en condiciones de integrarse; o **Request
changes**, si hay algo que corregir antes.

Quien abrió el PR responde cada comentario, aplicando el cambio pedido o
explicando por qué no corresponde. Para aplicar correcciones no hace falta
otro PR: se hacen nuevos commits en la misma rama y se suben, y el PR se
actualiza solo.

```bash
$ git commit -m "Renombrar la función de validación según la revisión"
$ git push
```

Cada conversación resuelta se marca con *Resolve conversation*. Integrar un
PR con comentarios sin responder equivale a no haber pedido la revisión.

### Verificaciones automáticas

Muchos repositorios ejecutan automáticamente las pruebas cada vez que se
sube un commit a un PR, y GitHub muestra el resultado en el propio PR: una
marca verde si pasaron, roja si algo falló. Además, la rama `main` suele
estar protegida con reglas como "no se puede integrar sin al menos una
aprobación y con todas las verificaciones en verde", de modo que nadie
pueda saltearse la revisión.

### Mantener el PR actualizado

Si mientras el PR espera revisión `main` recibe cambios en los mismos
archivos, GitHub avisa que la rama está desactualizada o que tiene
conflictos. Se resuelve trayendo `main` a la rama, como en cualquier
merge:

```bash
$ git switch fix/email-con-mas
$ git fetch
$ git merge origin/main
# resolver conflictos si los hay, probar
$ git push
```

### Integrar y limpiar

Con la aprobación y las verificaciones en verde, el PR se integra desde
GitHub. Hay tres opciones, que dejan historiales distintos en `main`.
**Create a merge commit** suma los commits de la rama junto con un commit
de merge (`Merge pull request #42 from empresa/fix/email-con-mas`): el
historial conserva cada commit original. **Squash and merge** junta todos
los commits de la rama en uno solo, con el título del PR (`Aceptar emails
con + en el registro (#42)`): el historial de `main` queda con un commit
por PR. **Rebase and merge** reaplica los commits de la rama a
continuación de `main`, sin commit de merge: el historial queda lineal.
Cada equipo elige una opción y la usa siempre, para que el historial sea
consistente.

Una vez integrado el PR, la rama ya no hace falta. GitHub ofrece borrarla
con *Delete branch*, y en la computadora se actualiza `main` y se borra la
rama local:

```bash
$ git switch main
$ git pull
$ git branch -d fix/email-con-mas
```

## Cuándo usarlo

Se abre un PR cada vez que una rama está lista para integrarse y el
cambio necesita revisión, que en un equipo es prácticamente siempre.

## Buenas prácticas

- Un PR por cambio, con un título que lo describa.
- Una descripción con qué cambia, por qué y cómo probarlo.
- Abrir como draft lo que todavía no está listo.
- Responder cada comentario antes de integrar.
- Actualizar el PR con `main` antes de integrarlo.

## Anti-patrones

- **Un PR que mezcla varios cambios sin relación**.
- **Integrar sin revisión ni aprobación**.
- **Dejar comentarios sin responder e integrar igual**.
- **Abrir un PR sin descripción**.
