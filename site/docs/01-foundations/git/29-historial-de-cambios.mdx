## Conceptos

Un historial solo es útil si se sabe consultarlo. Tres comandos cubren
las consultas habituales: `git log` para ver la lista de commits, `git
diff` para ver qué cambió línea por línea y `git checkout` para revisar
el código tal como estaba en un commit anterior. Los ejemplos usan el
repositorio de una aplicación de turnos médicos.

### `git log`: la lista de commits

```bash
$ git log
commit e41b7c2a9d0f3e5b7c1a2d4f6e8b0c2d4f6a8b0c
Author: Lucía Pérez <lucia@empresa.com>
Date:   Tue Oct 28 09:02:11 2026 -0300

    Ordenar los turnos por fecha en la agenda

commit c08d1f5e3b2a7c9d1e0f4a6b8c2d0e3f5a7b9c1d
Author: Diego Ruiz <diego@empresa.com>
Date:   Mon Oct 27 16:45:30 2026 -0300

    Permitir cancelar un turno hasta 2 horas antes
```

Los commits aparecen del más reciente, arriba, al más antiguo, abajo.
Cuando la lista no entra en la pantalla, la terminal la muestra por
partes: se avanza con las flechas o la barra espaciadora y se sale con
`q`.

La salida completa es extensa. Estas opciones la ajustan a lo que se
necesita, y se pueden combinar:

```bash
$ git log --oneline             # una línea por commit: id corto y mensaje
$ git log -5                    # solo los últimos cinco commits
$ git log -- turnos.ts          # solo los commits que modificaron ese archivo
$ git log --author="Lucía"      # solo los commits de esa persona
$ git log --stat                # además, qué archivos tocó cada commit
```

```bash
$ git log --oneline -3
e41b7c2 Ordenar los turnos por fecha en la agenda
c08d1f5 Permitir cancelar un turno hasta 2 horas antes
7a6e3b9 Agregar test del turno superpuesto
```

La combinación `git log --oneline -- turnos.ts` da la historia resumida de
un único archivo, y es la consulta que conviene hacer antes de modificar
código que no se escribió: muestra quién lo cambió, cuándo y con qué
motivo. También resuelve discusiones que de otro modo dependen de la
memoria ("¿esto siempre funcionó así o se cambió hace poco?").

Para ver un commit puntual completo, con su mensaje y todos sus cambios,
se usa `git show` con su identificador:

```bash
$ git show c08d1f5
```

### `git diff`: qué cambió, línea por línea

`git diff` compara dos versiones y muestra las diferencias. Sin
argumentos, compara lo que se modificó en el working directory con el
último commit:

```bash
$ git diff
diff --git a/envio.ts b/envio.ts
--- a/envio.ts
+++ b/envio.ts
@@ -12,7 +12,7 @@ export function costoDeEnvio(peso: number) {
   const base = 800;
-  const PESO_PESADO = 10;
+  const PESO_PESADO = 1;
   return peso > PESO_PESADO ? base * 2 : base;
 }
```

La salida se lee así. Las líneas que empiezan con `-` (en rojo en la
terminal) son las que estaban y se quitaron; las que empiezan con `+` (en
verde) son las nuevas; las que no tienen signo son **contexto**, líneas
sin cambios que se muestran para ubicar la modificación. La línea `@@`
indica en qué parte del archivo está el fragmento. En este ejemplo, el
diff revela algo que conviene detectar antes de confirmar: el umbral de
peso pasó de 10 a 1, probablemente por un error de tipeo, y con eso casi
todos los envíos pasarían a costar el doble. Leer también el contexto
importa: un cambio en una línea puede afectar a la siguiente, aunque esa
no haya cambiado.

Lo que compara `git diff` depende de cómo se lo llame:

```bash
$ git diff                     # cambios todavía no agregados al staging
$ git diff --staged            # cambios ya agregados: lo que va a entrar en el commit
$ git diff envio.ts            # lo mismo que el primero, limitado a un archivo
$ git diff 7a6e3b9 e41b7c2     # diferencias entre dos commits
```

La diferencia entre las dos primeras formas es una fuente frecuente de
confusión. Una vez que un archivo se agregó con `git add`, el `git diff`
sin opciones deja de mostrarlo, porque ya no es un cambio suelto. Para
revisar exactamente lo que va a entrar en el commit hace falta `git diff
--staged`. Revisar el diff antes de cada commit evita confirmar sin
querer una línea de prueba olvidada, un valor cambiado por error o un
archivo de configuración local.

`git diff` muestra qué cambió, pero no quién. Para eso está `git blame`,
que indica, línea por línea, en qué commit y por quién se escribió cada
una:

```bash
$ git blame turnos.ts
c08d1f5 (Diego Ruiz   2026-10-27) const HORAS_MINIMAS = 2;
7a6e3b9 (Lucía Pérez  2026-10-25) export function puedeCancelar(turno: Turno) {
```

### `git checkout`: ver una versión anterior

Para comprobar cómo funcionaba algo antes de un cambio, se puede volver
el working directory al estado de un commit anterior:

```bash
$ git checkout 7a6e3b9
Note: switching to '7a6e3b9'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.
```

Los archivos quedan exactamente como estaban en ese commit, y se puede
ejecutar la aplicación para comparar. El mensaje advierte que el
repositorio quedó en estado **detached HEAD**: HEAD apunta a un commit
suelto, no a una rama. Mirar y probar es seguro. Lo riesgoso es editar y
confirmar en ese estado, porque esos commits no quedan en ninguna rama y
se pierden de vista al volver.

Para volver a la rama de trabajo:

```bash
$ git switch main
```

En versiones antiguas de Git, el mismo resultado se obtiene con `git
checkout main`. Si después de revisar el commit anterior hace falta
trabajar a partir de ese punto, lo correcto es crear una rama desde ahí,
como se ve en la lección de ramas.

## Cuándo usarlo

`git log` y `git diff` se usan de forma rutinaria: antes de cada commit,
para revisar qué se va a incluir, y antes de modificar un archivo
desconocido, para entender su historia. `git checkout` a un commit
anterior se usa para investigar un estado puntual del pasado, no como
forma habitual de trabajo.

## Buenas prácticas

- Revisar el diff antes de cada commit, con `--staged` si ya se agregó.
- Consultar el historial de un archivo antes de modificarlo.
- Resolver con `git log` las dudas sobre cuándo cambió algo.
- Leer también las líneas de contexto de un diff.

## Anti-patrones

- **Confirmar sin revisar el diff**.
- **Modificar un archivo sin mirar su historia**.
- **Editar y confirmar en estado detached HEAD**.
- **Discutir de memoria lo que el historial responde con un comando**.
- **Leer solo las líneas cambiadas de un diff**, sin su contexto.
