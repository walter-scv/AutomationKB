## Conceptos

Ya sabés confirmar cambios y revisar el historial. Pero todos esos
commits, hasta ahora, viven en una sola línea de trabajo. Una **rama**
(branch) es una línea de trabajo independiente dentro del mismo
repositorio. `main` (o `master`) es la rama principal — la que
normalmente refleja el código "estable", el que usa o revisa el resto del
equipo.

```bash
git branch validar-contraseña
git checkout validar-contraseña
```

El primer comando crea la rama; el segundo cambia a ella. Se puede hacer
en un solo paso:

```bash
git checkout -b validar-contraseña
```

Trabajar en una rama propia permite cambiar, deshacer o romper cosas sin
afectar lo que el resto del equipo tiene en `main`.

## Cuándo usarlo

Siempre que vayas a hacer un cambio, por chico que sea, conviene crear una
rama antes de tocar nada — no solo para cambios grandes. El costo de crear
una rama es mínimo, y evita que un cambio a medio terminar quede mezclado
con el código estable que el resto del equipo está usando.

## Buenas prácticas

- **Una rama por cambio**, con un nombre que describa qué contiene
  (`feature/validar-contraseña`, `fix/operador-comparacion`) — así se
  revisa y se mergea sin arrastrar nada más.
- **Crear la rama antes de empezar a editar, no después** — si ya
  empezaste a cambiar algo directo en `main`, pasar esos cambios a una
  rama propia es más trabajoso que haberla creado primero.
- **Mantener la rama corta: mergearla apenas el cambio esté listo**, no
  dejarla viviendo semanas — cuanto más tiempo pasa, más se aleja de
  `main` y más conflictos acumula para el día que se mergee.
- **Borrar la rama después de mergearla** — una rama vieja que sigue ahí
  no aporta nada y genera confusión sobre cuáles siguen activas.
- **Crear la rama a partir de `main` recién actualizado**
  (`git pull` antes de `git checkout -b`), no de una rama vieja propia o
  de otra persona que todavía no se mergeó.

## Anti-patrones

- **Nombres de rama que no dicen nada** (`rama2`, `prueba`, `temp`) — en
  una semana nadie sabe qué cambio contienen sin abrirlas.
- **Trabajar directo en `main`**, sin ninguna rama propia — mezcla
  cualquier cambio a medio terminar con el código que el resto del equipo
  usa.
- **Mezclar varios cambios sin relación en una misma rama**, el mismo
  problema de un commit gigante, pero a nivel rama: difícil de revisar y
  de mergear.
- **Dejar ramas viejas sin mergear ni borrar acumulándose** en el
  repositorio, sin que nadie sepa cuáles siguen teniendo trabajo pendiente.
- **Crear una rama a partir de otra rama vieja** en vez de `main`
  actualizado — arrastra cambios que todavía no se revisaron y complica el
  merge final.
