## Conceptos

Hasta acá todos los commits se hicieron sobre una única línea de trabajo.
En un equipo, varias personas trabajan al mismo tiempo en cambios
distintos, y no conviene que un cambio a medio terminar quede mezclado con
el código que usa el resto. Las **ramas** resuelven ese problema.

### Qué es una rama

Una **rama** es una línea de trabajo independiente dentro del mismo
repositorio. La rama principal, normalmente llamada `main` (en proyectos
más antiguos, `master`), contiene el código estable: el que se integra,
se prueba y se libera. Cuando se crea una rama nueva, arranca desde el
commit en el que se está parado y, a partir de ahí, avanza por su cuenta:

```text
                 ●───●        fix/telefono-con-guiones
                /
●───●───●───●───●───●         main
```

Los commits que se hagan en `fix/telefono-con-guiones` no afectan a
`main`, y los que el equipo sume a `main` no afectan a la rama. Cuando el
cambio está listo, se integra a `main` (el *merge*, en la lección
siguiente). Mientras tanto, se puede probar, corregir o descartar sin
consecuencias para nadie más.

### Ver las ramas

```bash
$ git branch
  feature/historial-de-pagos
* fix/telefono-con-guiones
  main
```

`git branch` lista las ramas locales y marca con `*` aquella en la que se
está trabajando, que es a la que apunta HEAD. `git status` lo indica
también en su primera línea: `On branch fix/telefono-con-guiones`.

### Crear una rama y cambiar de rama

`git branch <nombre>` crea una rama pero no cambia a ella; `git switch
<nombre>` cambia a una rama existente. Como casi siempre se quieren las
dos cosas, `git switch -c` crea la rama y cambia a ella en un paso:

```bash
$ git switch -c fix/telefono-con-guiones
Switched to a new branch 'fix/telefono-con-guiones'
```

Muchos equipos y tutoriales usan el comando más antiguo, `git checkout`,
que hace lo mismo con otra sintaxis: `git checkout main` cambia a `main`,
y `git checkout -b fix/telefono-con-guiones` crea la rama y cambia a ella.
Los dos funcionan igual. `git switch` se incorporó para separar el cambio
de rama de otras funciones que tiene `checkout`, y es un poco más difícil
de usar por error.

### Desde dónde crear la rama

Como una rama arranca desde el commit actual, importa en qué rama y en qué
estado se está al crearla. Si se crea estando en `feature/historial-de-pagos`,
una rama de otra persona que todavía no se integró, la rama nueva arrastra
todos esos commits sin revisar, y el merge final se complica. Si se crea
desde un `main` desactualizado, se trabaja sobre código viejo y los
conflictos aparecen recién al integrar. La secuencia habitual es:

```bash
$ git switch main                       # pararse en main
$ git pull                              # traer lo último del remoto
$ git switch -c fix/telefono-con-guiones
```

(`git pull` trae los cambios del repositorio remoto; se ve en detalle en
esa lección.)

### Cambiar de rama con cambios sin confirmar

Si hay cambios sin confirmar al cambiar de rama, Git intenta llevarlos al
working directory de la otra rama. Si esos cambios chocan con algo
distinto en la rama de destino, se niega a cambiar:

```text
error: Your local changes to the following files would be overwritten by checkout:
        perfil.ts
Please commit your changes or stash them before you switch branches.
```

El mensaje indica las dos salidas: confirmar el cambio o guardarlo
temporalmente con `git stash` (que se ve en la lección sobre deshacer
cambios).

### Nombres de ramas

El nombre de una rama tiene que decir qué contiene, para que cualquiera lo
entienda sin abrirla. La convención más extendida usa un prefijo según el
tipo de cambio, seguido de una descripción corta en minúsculas, con
guiones: `feature/` para funcionalidades nuevas (`feature/historial-de-pagos`),
`fix/` para correcciones (`fix/telefono-con-guiones`), `docs/` para
documentación. Nombres como `prueba`, `rama2`, `temp` o `cambios` no
informan nada: a la semana nadie sabe qué tienen ni si siguen haciendo
falta.

### Borrar y renombrar ramas

Una vez integrada, una rama se borra:

```bash
$ git branch -d fix/telefono-con-guiones
Deleted branch fix/telefono-con-guiones (was 7f8e9d0).
```

La opción `-d` es segura: si la rama tiene commits que no llegaron a
ninguna otra rama, Git se niega a borrarla y lo explica:

```text
error: the branch 'feature/historial-de-pagos' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D feature/historial-de-pagos'
```

`-D`, en mayúscula, borra la rama de todas formas, y sus commits sin
integrar quedan perdidos de vista. Se usa solo cuando se tiene la certeza
de que ese trabajo no hace falta. Tampoco se puede borrar la rama en la
que se está parado: primero hay que cambiar a otra. Para corregir el
nombre de una rama, `git branch -m` recibe el nombre actual y el nuevo:
`git branch -m fix/telefono fix/telefono-con-guiones`.

## Cuándo usarlo

Se crea una rama para cualquier cambio, por chico que sea, antes de
empezar a editar. El costo de crearla es nulo, y evita que un cambio a
medio terminar quede mezclado con el código estable.

## Buenas prácticas

- Una rama por cambio, con un nombre que describa qué contiene.
- Crear la rama antes de editar, desde `main` actualizado.
- Integrar la rama apenas el cambio está listo, sin dejarla semanas.
- Borrar la rama una vez integrada.

## Anti-patrones

- **Trabajar directo en `main`**.
- **Nombres que no dicen nada** (`rama2`, `temp`).
- **Mezclar varios cambios sin relación en una rama**.
- **Acumular ramas viejas sin integrar ni borrar**.
- **Crear una rama a partir de otra rama sin integrar**.
