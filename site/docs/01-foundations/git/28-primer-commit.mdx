## Conceptos

Ya viste qué es un repositorio y los conceptos centrales de Git: working
directory, staging area y commit. Cuatro comandos alcanzan para crear un
repositorio y confirmar el primer cambio:

```bash
git init
```

Convierte la carpeta actual en un repositorio: a partir de acá, Git empieza
a llevar historial de lo que pasa ahí. Se ejecuta una sola vez por
proyecto.

```bash
git status
```

Muestra el estado actual: qué archivos cambiaron, cuáles ya están en el
staging area y cuáles todavía no. Se puede ejecutar en cualquier momento,
sin que cambie nada — solo informa.

```bash
git add validarContraseña.ts
```

Mueve ese archivo al staging area: lo marca como listo para el próximo
commit. `git add .` hace lo mismo con todos los archivos cambiados.

```bash
git commit -m "Agregar validación de longitud de contraseña"
```

Confirma lo que está en el staging area, con un mensaje que describe el
cambio. A partir de acá, ese cambio queda guardado en el historial.

## Cuándo usarlo

`git init` se ejecuta una sola vez, al arrancar un proyecto nuevo (o para
convertir en repositorio una carpeta que todavía no lo era). El ciclo
`status` → `add` → `commit` se repite cada vez que hay un cambio para
guardar, por chico que sea.

## Buenas prácticas

- **Escribir el mensaje en términos de qué cambió**, no de cómo se sintió
  hacerlo ("Agregar validación de longitud de contraseña", no "cambios" ni
  "fix") — el historial solo sirve si se puede leer meses después sin
  abrir cada diff.
- **Ejecutar `git status` antes de `git add`**, para confirmar exactamente
  qué se está por incluir, en vez de asumirlo.
- **Un commit, un cambio**: si se corrigieron dos cosas sin relación,
  conviene dos commits separados — así se puede revertir uno sin arrastrar
  el otro.
- **Confirmar apenas termina una unidad de cambio**, no acumular horas de
  trabajo sin commitear — un commit gigante es tan difícil de revisar como
  de revertir parcialmente.
- **Agregar archivo por archivo cuando los cambios no están relacionados**,
  en vez de `git add .` a ciegas, para no terminar mezclando sin querer
  cosas que debían ir en commits distintos.

## Anti-patrones

- **Mensajes genéricos** ("cambios", "fix", "update") que no dicen qué se
  modificó — obligan a abrir el diff cada vez que alguien necesita saber
  qué pasó.
- **`git add .` sin haber mirado `git status` antes**, que puede incluir
  archivos que no correspondían (una credencial local, un archivo de
  configuración de tu editor).
- **Mezclar cambios sin relación en un solo commit**, lo que hace más
  difícil revertir uno sin afectar al otro.
- **Confirmar código que no compila o con tests fallando**, rompiendo la
  garantía de que cualquier commit del historial es un punto al que se
  puede volver con seguridad.
- **Esperar a "tener todo perfecto" para el primer commit**, perdiendo
  justo el beneficio de empezar a versionar desde el principio.
