## Conceptos

`git merge` integra dos ramas creando, cuando las dos avanzaron, un
commit de merge que las une. `git rebase` integra los mismos cambios de
otra manera: en lugar de unir las dos líneas, **mueve los commits** de una
rama para que queden a continuación de lo último de la otra. El resultado
es un historial lineal, pero se obtiene reescribiendo commits, y eso
define cuándo se puede usar.

### Merge y rebase, sobre el mismo caso

La rama `feature/favoritos` tiene dos commits, `A` y `B`. Mientras tanto,
`main` sumó otros dos, `X` e `Y`:

```text
           A───B         feature/favoritos
          /
●───●───X───Y            main
```

Con `git merge main`, estando en la rama, se crea un commit de merge `M`
con dos padres. `A` y `B` no cambian:

```text
           A───B───M     feature/favoritos
          /       /
●───●───X───Y─────       main
```

Con `git rebase main`, en cambio, Git toma los commits de la rama y los
vuelve a aplicar, uno por uno, a continuación de `Y`:

```text
                  A'───B'    feature/favoritos
                 /
●───●───X───Y             main
```

El historial queda en línea, sin el commit de merge. Pero `A'` y `B'` no
son `A` y `B`: tienen los mismos cambios, con otro padre y, por lo tanto,
otro identificador. Los commits originales fueron reemplazados. Si alguien
más había descargado `A` y `B`, su copia de la rama ya no coincide con la
del remoto.

### Hacer un rebase

Estando en la rama propia, se indica sobre qué rama reaplicar los
commits. Lo habitual es la versión más reciente de `main` en el remoto, que
se obtiene antes con un `fetch`:

```bash
$ git switch feature/favoritos
$ git fetch
$ git rebase origin/main
Successfully rebased and updated refs/heads/feature/favoritos.
```

### Conflictos durante un rebase

Como los commits se reaplican de a uno, un conflicto detiene el rebase en
el commit que choca:

```text
Auto-merging favoritos.ts
CONFLICT (content): Merge conflict in favoritos.ts
error: could not apply 6e1f3a2... Guardar favoritos en el perfil
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
```

La resolución del archivo es igual que en un merge: leer las dos
versiones, dejar la correcta, quitar las marcas y probar. Lo que cambia es
cómo se continúa. En lugar de `git commit`, se marca el archivo como
resuelto y se le indica a Git que siga con el commit siguiente:

```bash
$ git add favoritos.ts
$ git rebase --continue
```

Si otro commit choca más adelante, el rebase se vuelve a detener y se
repite el procedimiento. Una ventaja de este mecanismo es que cada
conflicto se resuelve en el contexto del commit que lo produjo, en lugar
de todos juntos como en un merge. `git rebase --abort` cancela el rebase y
deja la rama exactamente como estaba antes de empezar. Lo que no
corresponde es abandonarlo a mitad de camino: mientras esté en curso, `git
status` informa `interactive rebase in progress` y la rama queda en un
estado intermedio.

### `git pull --rebase`

Un `git pull` hace un merge de lo que trae. Si hay commits locales que
todavía no se subieron, cada sincronización agrega un commit de merge al
historial. La opción `--rebase` reemplaza ese merge por un rebase: trae los
commits del remoto y reaplica los locales a continuación.

```bash
$ git pull --rebase
```

Es seguro siempre que los commits que se reaplican sean propios y todavía
no estén en el remoto.

### Subir una rama después de un rebase

Si la rama ya estaba en el remoto, después del rebase sus commits son
distintos de los que tiene el remoto, y un `git push` común se rechaza.
Para subirla hay que forzar el push, y la forma segura de hacerlo es:

```bash
$ git push --force-with-lease
+ 9a1b2c3...7f8e9d0 feature/favoritos -> feature/favoritos (forced update)
```

`--force-with-lease` reemplaza la rama del remoto solo si sigue exactamente
como estaba la última vez que se la consultó. Si alguien subió un commit a
esa rama mientras tanto, se niega y lo informa:

```text
 ! [rejected]        feature/favoritos -> feature/favoritos (stale info)
```

`--force` a secas no hace esa comprobación: reemplaza el remoto de todos
modos, y el commit del compañero desaparece de él.

### Cuándo se puede rebasear

La regla se desprende de que el rebase reescribe commits. En una rama
propia que nunca se subió, se puede rebasear sin restricciones, porque
nadie más tiene esos commits. En una rama propia que ya se subió pero que
nadie más usa, también, avisando y subiéndola después con
`--force-with-lease`. En una rama que otra persona ya descargó y sobre la
que trabaja, no: sus commits quedarían desincronizados, y lo correcto es
integrar con merge. Y en `main`, o en cualquier rama compartida por el
equipo, nunca.

Que el rebase deje un historial más prolijo no lo convierte en la opción
por defecto. Cuando un merge alcanza, es más seguro: no reescribe nada.

## Cuándo usarlo

El rebase conviene para actualizar una rama propia con lo último de `main`
antes de abrir un Pull Request, de modo que el historial quede lineal, o
para sincronizar con `pull --rebase` commits locales todavía no subidos.
En ramas compartidas, siempre merge.

## Buenas prácticas

- Rebasear solo ramas propias que nadie más descargó.
- Resolver cada conflicto en su commit y probar antes de continuar.
- Re-subir con `--force-with-lease`, nunca con `--force`.
- Avisar al equipo antes de reescribir una rama que ya está en el remoto.

## Anti-patrones

- **Rebasear una rama compartida**, incluida `main`.
- **Usar `--force` en lugar de `--force-with-lease`**.
- **Abandonar un rebase a mitad de camino**.
- **Rebasear por costumbre** cuando un merge alcanzaba.
