## El problema: código repetido entre pantallas

Imaginá una app con dos pantallas, `DashboardPage` y `SettingsPage`. Las
dos necesitan navegar a su URL y esperar a que cargue — y las dos repiten
el mismo código, cambiando solo la ruta final.

<Compare
  bad={{
    code: `class DashboardPage {
  async navigate() {
    await this.page.goto('https://app.example.com/dashboard');
  }
}
class SettingsPage {
  async navigate() {               // idéntico, copiado
    await this.page.goto('https://app.example.com/settings');
  }
}`,
    explanation: 'Con dos pantallas no duele. Con veinte, el mismo método está pegado veinte veces.',
  }}
  good={{
    code: `abstract class BasePage {
  constructor(protected page: Page, protected url: string) {}
  async navigate() { await this.page.goto(this.url); }
}
class DashboardPage extends BasePage { /* hereda navigate() */ }
class SettingsPage extends BasePage { /* hereda navigate() */ }`,
    explanation: 'navigate() existe una sola vez. Si mañana cambia la estrategia de espera, se cambia acá y las veinte Page Objects lo reciben sin tocarlas.',
  }}
/>

## Qué va en BasePage, y qué no

La regla es simple: si el comportamiento es **el mismo para cualquier
pantalla**, va en `BasePage`. Si depende de qué hace *esta* pantalla en
particular, va en la Page Object concreta.

## Cuándo el helper genérico no alcanza

No todo lo que parece repetido encaja en un helper común. Un campo de
cantidad que solo reacciona a eventos de tecla reales es un buen ejemplo:

<Compare
  bad={{
    code: `await this.fill(this.quantityInput, '5'); // BasePage.fill() genérico`,
    explanation: 'fill() pone el valor sin disparar los eventos de tecla que este campo necesita para reaccionar.',
  }}
  good={{
    code: `await this.quantityInput.clear();
await this.quantityInput.pressSequentially('5'); // tecla por tecla`,
    explanation: 'Esto no es un bug del helper genérico — es la señal correcta de que esta pantalla necesita algo más específico.',
  }}
/>
