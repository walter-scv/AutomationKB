Una suite lenta se corre poco. Esta entrada muestra cómo correr varios tests a la vez dentro de una máquina, qué cambia en los datos cuando los tests corren en paralelo, y cómo repartir la suite entre varias máquinas con un solo reporte al final.

## Conceptos

### El tiempo de la suite

Una suite que tarda una hora se corre menos de lo que debería: nadie la
espera antes de integrar un cambio, y los defectos llegan más lejos. El
catálogo de la biblioteca tarda un segundo en responder cada página. Sus
12 tests, uno detrás de otro:

```bash
npx playwright test --workers=1
```

```text
Running 12 tests using 1 worker
  12 passed (22.4s)
```

Casi todo ese tiempo es espera: el navegador aguarda al servidor. Correr
varios tests al mismo tiempo aprovecha esa espera.

### Workers

Un **worker** es un proceso que corre tests, con su propio navegador
(entrada de hooks y aislamiento). Con varios workers, varios tests corren
a la vez:

```bash
npx playwright test --workers=4
```

```text
Running 12 tests using 4 workers
  12 passed (6.9s)
```

De 22,4 a 6,9 segundos, sin cambiar ningún test. La cantidad se elige en
la configuración (entrada de configuración) o con `--workers` en el
comando, que le gana a la configuración:

```ts
workers: process.env.CI ? 2 : undefined,
```

- Un número fija la cantidad de workers.
- Un porcentaje, como `'50%'`, la calcula según los núcleos del
  procesador de la máquina.
- `undefined` deja el valor por defecto de Playwright: la mitad de los
  núcleos.

Más workers no siempre es más rápido. Cada uno abre un navegador y
consume memoria y procesador, y todos le piden al mismo servidor de
pruebas: si el servidor se satura, los tests empiezan a fallar por
tiempo. Una máquina de CI con dos núcleos rinde poco con ocho workers.

### Cómo se reparten los tests

Por defecto, Playwright reparte **archivos** entre los workers, y los
tests de un mismo archivo corren en orden, en el mismo worker (entrada de
hooks y aislamiento). Con cuatro archivos de tres tests y cuatro workers,
cada worker toma un archivo.

`fullyParallel: true` en la configuración (o `--fully-parallel` en el
comando) reparte cada **test** por separado. Sirve cuando un archivo
tiene muchos más tests que los demás: sin la opción, ese archivo lo corre
un solo worker mientras los otros terminan y esperan. En el catálogo, con
los archivos parejos, no ayuda:

```bash
npx playwright test --workers=4 --fully-parallel
```

```text
Running 12 tests using 4 workers
  12 passed (7.8s)
```

Para un solo archivo, `test.describe.configure({ mode: 'parallel' })` al
principio hace que sus tests se repartan, sin cambiar el resto de la
suite.

### Los datos en paralelo

Correr en paralelo expone un problema que en serie no se ve: dos tests al
mismo tiempo sobre los mismos datos. La suite de la biblioteca pasa con
un worker, y con cuatro falla:

```text
Running 8 tests using 4 workers
  ✘  4 [chromium] › tests/prestamos.spec.ts:5:7 › Préstamos › renovar un préstamo extiende el vencimiento 14 días @smoke @p0 @prestamos (197ms)
  ✘  3 [chromium] › tests/vencimientos.spec.ts:12:9 › Vencimiento al renovar › un préstamo que vence el 10/11 pasa al 24/11 @p1 @prestamos (195ms)

    Error: strict mode violation: getByRole('listitem').filter({ has: getByRole('heading', { name: 'Rayuela' }) }).getByText(/^Vence el/) resolved to 2 elements:
        1) <p>Vence el 10/11</p> aka getByText('Vence el 10/').nth(1)
        2) <p>Vence el 10/11</p> aka getByText('Vence el 10/').nth(2)
```

Los dos tests sembraron un préstamo de «Rayuela» para la misma socia, al
mismo tiempo, y cada uno encontró dos. No es un defecto de la aplicación
ni de Playwright: los tests no eran independientes de verdad (entrada de
setup y cleanup).

La corrección es que cada test use datos que solo él toca. El builder
agrega al título un sufijo único:

```ts
build(): Prestamo {
  const unico = `${test.info().parallelIndex}-${Date.now()}`;
  return { ...this.prestamo, titulo: `${this.prestamo.titulo} ${unico}` };
}
```

- `test.info()` da información del test que está corriendo.
  `parallelIndex` es el número del worker, de 0 a la cantidad de workers
  menos uno: dos tests que corren al mismo tiempo nunca tienen el mismo.
- `Date.now()` son los milisegundos desde 1970: distingue los tests que
  corren uno después de otro en el mismo worker, y las corridas de
  distintas personas.

El test ya no escribe el título a mano: usa el que le devuelve la
fixture.

```ts
const prestamo = await sembrarPrestamo(unPrestamo().deLibro('Rayuela').queVence('10/11').build());
await prestamosPage.abrir();
await prestamosPage.renovar(prestamo.titulo);
```

```text
Running 8 tests using 4 workers
  8 passed (6.2s)
```

El préstamo sembrado se llama, por ejemplo, `Rayuela 1-1793299931249`.

### Tests que dependen del orden

Si un flujo está partido en varios tests que dependen uno del otro, no
pueden repartirse. `test.describe.configure({ mode: 'serial' })` los
corre en orden, en el mismo worker, y si uno falla, los siguientes no
corren:

```text
  ✓  1 [chromium] › tests/serie.spec.ts:4:7 › alta de socio en tres pasos › 1 completa los datos (1.1s)
  ✘  2 [chromium] › tests/serie.spec.ts:8:7 › alta de socio en tres pasos › 2 confirma el email (3.1s)
  -  3 [chromium] › tests/serie.spec.ts:12:7 › alta de socio en tres pasos › 3 elige la sede
  1 failed
  1 did not run
  1 passed (5.6s)
```

Es una salida, no la regla: un test que necesita que otro corra antes es
un test partido en dos (entrada de hooks y aislamiento). Lo correcto
casi siempre es que cada test prepare lo que necesita, con fixtures.

### Sharding: repartir entre máquinas

Los workers reparten la suite dentro de una máquina. Cuando una sola no
alcanza, **sharding** la divide entre varias: cada máquina corre una
parte, al mismo tiempo que las otras.

```bash
npx playwright test --shard=1/2
```

```text
Running 6 tests using 2 workers, shard 1 of 2
  6 passed (6.7s)
```

`--shard=1/2` significa «la primera de dos partes»; otra máquina corre
`--shard=2/2`. Sin `fullyParallel`, las partes se arman con archivos
enteros: si hay menos archivos que shards, algún shard queda vacío y no
corre nada. Con `fullyParallel`, se reparten tests sueltos y las partes
quedan más parejas. Cómo se lanzan las máquinas en CI se ve en la entrada
de CI con GitHub Actions.

### Unir los reportes

Cada shard produce su propio resultado, y el equipo necesita un solo
reporte. El reporter `blob` guarda los resultados de cada shard en un
archivo, y `merge-reports` los une:

```bash
npx playwright test --shard=1/2 --reporter=blob
```

Deja `blob-report/report-1.zip`. Con los archivos de todos los shards en
una carpeta, se arma el reporte final:

```bash
npx playwright merge-reports --reporter=html ./all-blob-reports
```

```text
processing test events
building final report
finished building report
```

El resultado es un `playwright-report/` con los 12 tests, como si
hubieran corrido en una sola máquina. Cada corrida con `blob` vacía la
carpeta `blob-report/` antes de escribir: los archivos de cada shard se
juntan en otra carpeta, que en CI es la descarga de los artefactos de
cada máquina.

## Cuándo usarlo

Workers desde el principio, con una cantidad que la máquina y el servidor
de pruebas soporten. `fullyParallel` cuando los archivos son desparejos.
Sharding cuando una máquina, con todos sus workers, sigue siendo lenta.

## Buenas prácticas

- Que cada test use datos que solo él toca.
- Medir la duración con distintos workers antes de fijar uno.
- Reservar el modo serial para flujos que no se pueden separar.
- Unir los reportes de los shards en uno solo.

## Anti-patrones

- **Bajar a un worker** para esconder un choque de datos.
- **Más workers que núcleos**, o que lo que el servidor de pruebas
  aguanta.
- **Tests encadenados** en modo serial por comodidad.
- **Un reporte por shard** que nadie junta.
