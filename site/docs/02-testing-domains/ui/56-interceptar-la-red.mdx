Detrás de cada pantalla hay pedidos al servidor que el usuario no ve. Playwright puede mirarlos, esperarlos y responderlos en lugar del servidor, y eso permite probar cómo reacciona la interfaz ante errores, listas vacías o datos raros.

## Conceptos

### Lo que pasa entre la página y el servidor

Una página moderna no trae todo en el HTML: después de cargar, pide
datos al servidor y los dibuja. El catálogo de la biblioteca hace esto al
abrirse:

```text
GET /api/libros?q=todos
→ 200 [{"titulo":"Rayuela","disponibles":2},{"titulo":"Ficciones","disponibles":0}]
```

Es un pedido a una **API**: la página pide datos (`GET`) a una dirección,
y el servidor responde con un código de estado (`200` es "todo bien",
`500`, "error del servidor", `503`, "servicio no disponible") y los datos en JSON (entrada de JSON). Con esa
respuesta, la página arma la lista: Rayuela con un botón Reservar y
Ficciones «Sin ejemplares».

Para un test de UI, esos pedidos son una oportunidad. Playwright puede
**interceptarlos**: mirarlos, esperarlos, o responderlos en lugar del
servidor. Eso permite probar lo que la pantalla hace con respuestas
difíciles de conseguir en el entorno real: un catálogo vacío, un error
del servidor, una conexión que se corta.

### Responder en lugar del servidor: `route` y `fulfill`

`page.route(patrón, función)` intercepta los pedidos cuya dirección
coincide con el patrón. La función recibe el pedido (`route`) y decide
qué hacer con él. `route.fulfill` lo responde sin que llegue al servidor:

```ts
test('un catálogo vacío muestra el aviso', async ({ page }) => {
  await page.route('**/api/libros*', (route) => route.fulfill({ json: [] }));
  await page.goto('/buscador');
  await expect(page.getByText('No hay libros para mostrar')).toBeVisible();
});
```

- El patrón usa comodines: `**` es cualquier cosa, incluidas barras, y
  `*` cualquier cosa dentro de una parte de la ruta. `'**/api/libros*'`
  coincide con `http://localhost:4321/api/libros?q=todos`.
- `{ json: [] }` responde con una lista vacía, con estado 200 y el tipo de
  contenido JSON.
- La ruta se registra **antes** del `goto`: el pedido sale al cargar la
  página, y si nadie lo está interceptando, llega al servidor.

Para un error, `status` y un cuerpo:

```ts
await page.route('**/api/libros*', (route) => route.fulfill({ status: 500, body: 'error' }));
await page.goto('/buscador');
await expect(page.getByText('No pudimos cargar el catálogo')).toBeVisible();
```

### Simular una conexión caída: `abort`

`route.abort()` corta el pedido como si la red hubiera fallado:

```ts
await page.route('**/api/libros*', (route) => route.abort());
await page.goto('/buscador');
await expect(page.getByText('No pudimos cargar el catálogo')).toBeVisible();
```

Con `fulfill` y `abort`, el test verifica lo que la persona ve cuando las
cosas salen mal, algo que en un entorno real depende de la suerte.

### Modificar la respuesta real

A veces conviene usar la respuesta del servidor y cambiar un solo dato.
`route.fetch()` hace el pedido real y devuelve la respuesta; la función la
modifica y la entrega:

```ts
await page.route('**/api/libros*', async (route) => {
  const response = await route.fetch();
  const libros = await response.json();
  libros[0].disponibles = 0;                       // Rayuela, sin ejemplares
  await route.fulfill({ response, json: libros });
});
await page.goto('/buscador');
await expect(page.getByRole('button', { name: 'Reservar' })).toHaveCount(0);
```

El resto de la respuesta (los demás libros, los encabezados) es el del
servidor; solo cambia lo que el test necesita.

### Cuando el patrón no coincide

Si el patrón no coincide con ninguna dirección, la ruta no intercepta
nada y no hay ningún error: el pedido llega al servidor real. Con
`'**/api/libro'` (sin la `s` ni el `*` final), la página recibe el
catálogo real y el test falla más adelante:

```text
Error: expect(locator).toBeVisible() failed

Locator: getByText('No hay libros para mostrar')
Expected: visible
Timeout: 5000ms
Error: element(s) not found
```

El error no dice nada de la red. Ante un fallo así, conviene revisar
primero el patrón; la pestaña Network del trace (entrada de debugging)
muestra la dirección exacta que pidió la página.

### Esperar y verificar pedidos

Sin cambiar nada, un test puede esperar una respuesta y leerla, con el
mismo patrón de "esperar antes de la acción" de las pestañas nuevas y las
descargas:

```ts
const respuestaPromise = page.waitForResponse('**/api/libros*');
await page.goto('/buscador');
const respuesta = await respuestaPromise;
expect(respuesta.ok()).toBeTruthy();
```

`respuesta.status()` da el código y `respuesta.json()` los datos. También
se puede esperar el **pedido** que hace la página, para verificar qué
mandó al servidor:

```ts
await page.goto('/buscador');
const pedidoPromise = page.waitForRequest('**/api/reservas');
await page.getByRole('button', { name: 'Reservar' }).click();
const pedido = await pedidoPromise;
expect(pedido.method()).toBe('POST');
expect(pedido.postDataJSON()).toEqual({ titulo: 'Rayuela', socia: 'lucia@biblio.test' });
await expect(page.getByText('Reserva R-1042')).toBeVisible();
```

`postDataJSON()` devuelve los datos enviados como objeto, y `toEqual`
compara objetos por su contenido, no por identidad. El test verifica dos
cosas distintas: que la página mandó los datos correctos, y que mostró el
código que devolvió el servidor.

### Simular sin perder el sentido del test

Un test que simula todas las respuestas ya no prueba la aplicación
completa, solo la pantalla. Eso es útil para los casos que el entorno real
no puede dar (errores, listas vacías, casos límite), pero el flujo
principal también necesita tests contra el servidor real. Playwright
recomienda simular, sobre todo, las dependencias de **terceros**, como un
servicio de pagos externo, que el equipo no controla.

## Cuándo usarlo

Para probar cómo responde la pantalla a errores, demoras, listas vacías y
datos raros que el entorno real no produce a pedido, y para verificar qué
datos manda la página al servidor.

## Buenas prácticas

- Registrar `page.route` antes de la navegación o la acción que hace el
  pedido.
- Simular lo que el entorno no puede dar, y mantener tests del flujo
  principal contra el servidor real.
- Usar `route.fetch()` para cambiar un solo dato de una respuesta real.
- Verificar el pedido con `waitForRequest` cuando lo que importa es qué se
  envió.

## Anti-patrones

- **Simular todas las respuestas** de todos los tests.
- **Registrar la ruta después del `goto`**: el pedido ya salió.
- **Patrones demasiado amplios**, como `'**/api/**'`, que interceptan
  pedidos que el test no pensaba tocar.
- **Esperar con `waitForTimeout`** a que llegue una respuesta, en lugar de
  `waitForResponse` o una assertion.
