Los tests de un mismo archivo suelen compartir el punto de partida: ingresar, abrir una pantalla. Esta entrada muestra cómo compartir esa preparación sin que un test dependa de otro, y por qué Playwright hace que cada test arranque de cero.

## Conceptos

### Cada test arranca de cero

Playwright le da a cada test un **contexto de navegador** nuevo: una
sesión aislada, como una ventana de incógnito, con sus propias cookies,
su propio almacenamiento local y su propio historial. La fixture `page`
es una pestaña dentro de ese contexto. Cuando el test termina, el contexto
se descarta.

En este ejemplo, el primer test guarda una preferencia en el
almacenamiento local de la página (`localStorage`), y el segundo la lee:

```ts
test('el primer test guarda una preferencia', async ({ page }) => {
  await page.goto('/catalogo');
  await page.evaluate(() => localStorage.setItem('vista', 'lista'));
  console.log('test 1:', await page.evaluate(() => localStorage.getItem('vista')));
});

test('el segundo test arranca sin esa preferencia', async ({ page }) => {
  await page.goto('/catalogo');
  console.log('test 2:', await page.evaluate(() => localStorage.getItem('vista')));
});
```

`page.evaluate` ejecuta código dentro de la página; acá se usa solo para
mirar el almacenamiento. Corriendo con `--workers=1`, los dos tests usan
el mismo worker, uno después del otro, y aun así el segundo no ve lo que
guardó el primero:

```text
test 1: lista
test 2: null
```

Lo mismo vale para una sesión iniciada: si un test ingresa con una
cuenta, el siguiente arranca sin sesión. Ese aislamiento es lo que
permite correr tests en paralelo y en cualquier orden. También significa
que cada test tiene que preparar todo lo que necesita.

### Un test que depende de otro

El aislamiento cubre el navegador, no el código. Una variable declarada
fuera de los tests es compartida, y tienta a pasar datos de un test al
siguiente:

```ts
let codigoReserva: string;

test('reservar un libro genera un código', async ({ page }) => {
  await page.goto('/catalogo');
  codigoReserva = 'R-1042';
});

test('consultar la reserva por su código', async ({ page }) => {
  await page.goto('/catalogo');
  expect(codigoReserva).toBe('R-1042');
});
```

(`expect(valor).toBe(...)` compara un valor común, no un elemento; se ve
en la entrada de assertions.) Por defecto, Playwright reparte los
**archivos** entre los workers y corre los tests de un mismo archivo en
orden, uno tras otro. La configuración que genera el instalador agrega
`fullyParallel: true` (entrada de configuración), y con esa opción
también los tests de un mismo archivo se reparten. Con un solo worker,
los dos tests corren en orden y pasan; con `fullyParallel` y varios
workers, no:

```text
Running 2 tests using 2 workers
  ✓  1 [chromium] › tests/dependiente.spec.ts:5:5 › reservar un libro genera un código (65ms)
  ✘  2 [chromium] › tests/dependiente.spec.ts:10:5 › consultar la reserva por su código (90ms)

    Error: expect(received).toBe(expected) // Object.is equality
    Expected: "R-1042"
    Received: undefined
```

Cada worker es un proceso separado, con su propia copia de la variable.
El segundo test corrió en otro worker, donde nadie le asignó un valor:
`undefined`. Lo mismo pasa si se corre solo el segundo test con `-g`, o
si el primero falla. No son dos tests independientes: es un test partido
en dos. La solución es que el segundo prepare su propia reserva, igual
que haría un caso de test manual con su precondición.

### Preparar antes de cada test: `beforeEach`

Cuando varios tests necesitan la misma preparación, repetirla en cada uno
los alarga y obliga a cambiarla en varios lugares. `test.beforeEach`
define un bloque que corre antes de **cada** test:

```ts
test.describe('Préstamos', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/login');
    await page.getByLabel('Email').fill('lucia@biblio.test');
    await page.getByLabel('Contraseña').fill('clave123');
    await page.getByRole('button', { name: 'Ingresar' }).click();
  });

  test('renovar un préstamo vigente extiende el vencimiento al 24/11', async ({ page }) => {
    await page.getByRole('button', { name: 'Renovar' }).click();
    await expect(page.getByRole('cell', { name: '24/11' })).toBeVisible();
  });

  test('la lista de préstamos muestra Rayuela', async ({ page }) => {
    await expect(page.getByRole('cell', { name: 'Rayuela' })).toBeVisible();
  });
});
```

El hook recibe las mismas fixtures que el test, y la `page` es la misma:
el test arranca donde el hook la dejó, con la sesión iniciada. Como el
hook corre para cada test, cada uno sigue teniendo su propio contexto; lo
que se evita es repetir el código, no la preparación.

Un hook dentro de un `test.describe` aplica solo a los tests de ese
grupo. Fuera de todo grupo, aplica a todos los tests del archivo.

### Limpiar después: `afterEach`

`test.afterEach` corre después de cada test, pase o falle. Se usa para
deshacer lo que el test dejó fuera del navegador, por ejemplo un registro
que creó en el sistema, para que no afecte a los tests siguientes ni a
otras personas que usan el mismo entorno. Lo que queda dentro del
navegador (cookies, almacenamiento) no hace falta limpiarlo: el contexto
se descarta solo.

### Una vez por worker: `beforeAll` y `afterAll`

`test.beforeAll` y `test.afterAll` corren una vez antes y una vez después
de un grupo de tests. Con `console.log` en cada hook y un solo worker, el
orden queda a la vista:

```text
Running 2 tests using 1 worker
beforeAll
beforeEach
test: buscar por título
afterEach
beforeEach
test: buscar sin resultados
afterEach
afterAll
```

`beforeAll` una vez al principio, el par `beforeEach`/`afterEach`
alrededor de cada test, y `afterAll` al final.

"Una vez" significa una vez **por worker**. Con `fullyParallel` y dos
workers, los tests del grupo se reparten y cada worker corre su propio
`beforeAll`:

```text
Running 2 tests using 2 workers
beforeAll
beforeAll
...
afterAll
afterAll
```

Por eso `beforeAll` no sirve para algo que tiene que pasar una sola vez
para toda la suite; eso se resuelve con otras herramientas que se ven en
la sección III. Sirve para preparar algo costoso que todos los tests del
grupo pueden compartir sin modificarlo, como leer un archivo con datos de
referencia.

`beforeAll` tampoco puede usar `page`: la página se crea para cada test,
y en ese momento no hay ningún test corriendo. Si se intenta, Playwright
lo rechaza:

```text
Error: "context" and "page" fixtures are not supported in "beforeAll" since they are created on a per-test basis.
If you would like to reuse a single page between tests, create context manually with browser.newContext(). See https://aka.ms/playwright/reuse-page for details.
If you would like to configure your page before each test, do that in beforeEach hook instead.
```

El propio mensaje da la salida habitual: preparar la página en
`beforeEach`.

## Cuándo usarlo

`beforeEach` cuando todos los tests de un grupo comparten el mismo punto
de partida, como ingresar y navegar a una pantalla. `afterEach` para
limpiar lo que un test creó fuera del navegador. `beforeAll` solo para
preparación costosa que los tests comparten sin modificar.

## Buenas prácticas

- Hacer que cada test prepare lo que necesita, directamente o con
  `beforeEach`.
- Dejar en el hook solo lo que comparten todos los tests del grupo.
- Limpiar en `afterEach` lo que un test crea fuera del navegador.
- Correr un test solo, con `-g`, para comprobar que no depende de otro.

## Anti-patrones

- **Pasar datos de un test a otro** con variables compartidas.
- **Confiar en el orden de los tests**: en paralelo, el orden cambia.
- **Usar `beforeAll` para algo que tiene que pasar una sola vez** en toda
  la suite.
- **Meter en `beforeEach` la acción que el test prueba**: el hook prepara,
  el test actúa y verifica.
