## El problema que resuelve

Imaginá dos tests que compran un producto en un checkout. Sin ningún
patrón, cada uno busca los elementos directamente en la pantalla:

```ts
// test A
await page.getByRole('spinbutton').first().fill('1');
await page.getByRole('button', { name: 'Confirmar compra' }).click();

// test B, en otro archivo, repite exactamente lo mismo
await page.getByRole('spinbutton').first().fill('5');
await page.getByRole('button', { name: 'Confirmar compra' }).click();
```

El día que el botón cambie de "Confirmar compra" a "Finalizar pedido", hay
que salir a buscar esa línea en cada test que la repite.

## Prioridad de selectores

Para escribir los métodos de una Page Object hay que elegir un selector —
y no todos envejecen igual. El criterio: **¿qué tan probable es que este
valor cambie por una razón que no tiene nada que ver con el comportamiento
que estoy probando?**

| Selector | Qué tan estable es |
|---|---|
| `getByTestId` | El más estable: es un atributo que solo existe para testing — nada más lo toca. |
| `getByRole` | Refleja la semántica del elemento. Sobrevive a cambios visuales. |
| `getByLabel` | Depende del label asociado — estable, pero varía con cambios de copy. |
| `getByPlaceholder` | El placeholder es texto de ayuda, de los primeros que cambia un diseñador. |
| `getByText` | El texto visible es lo que más cambia: rediseños, copy, traducciones. |
| CSS / XPath | Refleja la implementación interna del DOM — cambia por puro estilo. |

## Tres reglas para no arruinarlo

1. **Las aserciones van en el test, nunca en la Page Object.** La Page
   Object reporta estado; el test decide si ese estado es correcto.
2. **Métodos con significado de negocio, no pasos sueltos.**
   `clickConfirmarCompra()`, no un `click()` genérico.
3. **Los métodos reciben lo que les falta como parámetro, no lo
   adivinan.** Si `fillQuantity` no supiera de antemano cuánto va a
   comprar cada test, `quantity` tiene que ser un parámetro — igual que en
   cualquier función.
