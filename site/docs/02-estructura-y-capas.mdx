Un proyecto de automation maduro separa su código en piezas con una única
responsabilidad cada una — nunca todo junto, donde encontrar algo depende
de recordar dónde quedó.

## Las 4 capas

```
Test               → Arrange / Act / Assert. Lenguaje de negocio. Cero lógica.
Page Object        → Sabe interactuar con una pantalla. Expone acciones, no selectores.
Helper / Service   → Lógica compartida: llamadas a API, cálculos, formateo.
Data / Fixture     → Qué datos existen antes de que el test arranque.
```

No es una cadena estricta donde cada capa solo le habla a la siguiente —
un test puede llamar directo a un Helper para sembrar un dato antes de
arrancar (por ejemplo, un alta por API), sin que eso rompa nada. Lo que
nunca debería pasar es que una capa haga el trabajo de otra: que el test
busque sus propios selectores (trabajo de la Page Object) o convierta un
texto a mano (trabajo de un Helper).

## El error más común: una capa invade a otra

Cuando una de estas responsabilidades se cuela en el lugar equivocado —
casi siempre dentro del test — el síntoma es siempre el mismo: el test
sabe *cómo* está armada la pantalla, en vez de solo pedir *qué* resultado
espera.

Un chequeo rápido para detectarlo: leé el test tapando el código de la
Page Object que usa. Si se entiende qué verifica sin necesitar ver esa
implementación, la separación está funcionando. Si en cambio encontrás un
selector, una expresión regular o una cuenta matemática escritos directo
en el test, esa pieza vive en la capa equivocada.
