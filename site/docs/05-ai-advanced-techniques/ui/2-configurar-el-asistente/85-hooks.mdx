Una instrucción se puede ignorar y un permiso solo mira patrones. Un hook es código que corre siempre, en un momento fijo del trabajo del agente, y puede bloquearlo. Esta entrada muestra los eventos, cómo se configura, cómo se bloquea una acción y un caso real.

## Conceptos

### Instrucciones, permisos y lo que falta

Hasta acá hay dos formas de guiar a un agente:

- Las **instrucciones** del `CLAUDE.md` (entrada de instrucciones del
  proyecto): el agente las lee e intenta seguirlas, pero no lo obligan.
- Los **permisos** (entrada de permisos): bloquean o permiten una acción
  según un patrón fijo, como `Bash(git push *)`.

Hay reglas que ninguna de las dos resuelve. En la agenda, el equipo
quiere que el agente nunca use para ingresar una cuenta que no sea de
prueba. No alcanza con un patrón: hay que mirar el email que aparece en
el comando y compararlo con la lista de cuentas de prueba. Eso necesita
lógica, y tiene que cumplirse siempre. Para eso están los **hooks**.

Un aviso sobre el nombre: en la sección II viste los hooks de Playwright,
como `beforeEach`, que corren código antes o después de cada test. Los
hooks de Claude Code no tienen relación con esos: comparten la palabra
porque las dos cosas se «enganchan» (*hook*, en inglés) a un momento de
otro proceso.

### Qué es un hook

Un **hook** de Claude Code es un comando de la terminal que Claude Code
ejecuta solo, en un momento determinado del trabajo del agente. Esos
momentos se llaman **eventos**. Los más usados:

- `PreToolUse`: antes de que el agente use una herramienta, como correr
  un comando o editar un archivo. Puede bloquear esa acción.
- `PostToolUse`: después de que una herramienta terminó bien.
- `UserPromptSubmit`: cuando enviás un pedido, antes de que el agente lo
  lea.
- `SessionStart`: al empezar o retomar una sesión.
- `Stop`: cuando el agente termina de responder.

La diferencia con una instrucción es quién lo ejecuta: una instrucción
depende de que el agente decida cumplirla; un hook lo ejecuta Claude
Code, el programa, cada vez que ocurre el evento, decida lo que decida
el agente.

### Cómo se configura

Los hooks se escriben en la clave `hooks` de los mismos archivos
`settings.json` de los permisos. Cada uno dice en qué evento corre, para
qué herramientas (`matcher`, un patrón con sus nombres) y qué comando
ejecuta. Un ejemplo que no bloquea nada, para ver la forma:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }
        ]
      }
    ]
  }
}
```

Se lee así: después de cada vez que el agente edita (`Edit`) o crea
(`Write`) un archivo, correr ese comando. El comando usa tres
herramientas de la terminal:

- `jq` lee datos en formato JSON y extrae un campo: acá, la ruta del
  archivo que se editó;
- `xargs` le pasa esa ruta al comando siguiente;
- `npx prettier --write` formatea ese archivo con Prettier, el programa
  que acomoda sangrías, comillas y espacios según las reglas del
  proyecto.

Resultado: todo archivo que toca el agente queda formateado, sin
pedírselo.

### Cómo recibe los datos un hook

Para decidir, un hook necesita saber qué está por hacer el agente.
Claude Code se lo pasa como un texto JSON por la **entrada estándar**:
el canal por el que un programa de la terminal recibe datos de otro
programa, el mismo que usa `|` para pasarle la salida de un comando al
siguiente. En el evento `PreToolUse`, el JSON tiene un campo
`tool_input` con lo que el agente quiere hacer; para un comando de la
terminal, `tool_input.command` es el comando exacto.

### Bloquear una acción

Todo programa de la terminal termina con un **código de salida**: un
número que le dice a quien lo ejecutó cómo le fue. Por convención, 0
significa «todo bien» y cualquier otro número, un problema. Un hook usa
ese número para responderle a Claude Code:

- **0**: no tiene objeciones. La acción sigue, y después se aplican las
  reglas de permisos de siempre.
- **2**: bloquea la acción. Lo que el hook escribió en la **salida de
  errores** (el canal de los mensajes de error, que en bash se escribe
  con `>&2`) le llega al agente como explicación, para que corrija.
- **Otro código**: se considera un error del propio hook, y en la
  mayoría de los eventos la acción sigue igual.

Un hook que impide actualizar las imágenes de referencia del visual
testing (entrada de visual testing) sin revisar:

```bash
#!/bin/bash
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q -- "--update-snapshots"; then
  echo "Bloqueado: las imágenes de referencia se actualizan solo después de revisar el diff visual." >&2
  exit 2
fi

exit 0
```

Línea por línea: `INPUT=$(cat)` guarda el JSON que llegó por la entrada
estándar; la línea siguiente extrae el comando con `jq`; el `if` busca
`--update-snapshots` en el comando; si lo encuentra, escribe el motivo
en la salida de errores y termina con 2, y si no, termina con 0.

Para activarlo, el script se guarda en el repositorio, por ejemplo en
`.claude/hooks/no-update-snapshots.sh`, se le da permiso de ejecución
con `chmod +x .claude/hooks/no-update-snapshots.sh`, y se registra en
`.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/no-update-snapshots.sh" }
        ]
      }
    ]
  }
}
```

`"matcher": "Bash"` hace que corra antes de cada comando de la terminal.
El script usa `jq`, que no viene instalado en todas las computadoras: en
macOS se instala con `brew install jq`, y en Ubuntu con
`sudo apt install jq`. Si falta, `jq` no extrae nada, el `if` no
encuentra el texto y el script termina con 0: el hook deja pasar todo,
sin avisar. Es un caso de fallar abierto, que se ve más abajo.

Un hook que sale con 2 bloquea antes de que se miren las reglas `allow`:
aunque un permiso habilite el comando, el hook lo frena.

### Un caso real: solo cuentas de prueba

En un proyecto donde trabajamos, el `CLAUDE.md` tenía las credenciales
del entorno de pruebas de una persona del equipo, algo que de entrada no
tenía que estar ahí (entrada de instrucciones del proyecto). Al explorar la
aplicación, el agente usaba esa cuenta, y las conclusiones salían mal:
esa persona tenía permisos y datos distintos de los de las cuentas de
prueba que usa la suite. La instrucción «usá solo las cuentas de prueba»
no alcanzó. La solución fue un hook `PreToolUse` con una regla
**positiva**:

- si la acción contiene un email, ese email tiene que estar en el
  archivo de cuentas de prueba (`.env.test`);
- si está, termina con 0; si no, termina con 2 y le explica al agente que
  use una cuenta de prueba;
- los emails que nunca se usan para ingresar, como los de `noreply`, se
  ignoran.

Una regla positiva («solo estas») es más segura que una lista de
prohibidos («estas no»): una cuenta nueva que nadie agregó a la lista
queda bloqueada sola.

### Fallar abierto o cerrado

¿Qué hace el hook si no puede decidir, por ejemplo si no encuentra el
archivo de cuentas? Hay dos opciones:

- **Fallar abierto**: deja pasar. El trabajo no se frena, pero en ese
  caso la protección no existe.
- **Fallar cerrado**: bloquea. No se escapa nada, pero un archivo
  faltante frena todo.

El hook del caso real falla abierto cuando no encuentra el archivo,
porque corre en todos los proyectos de esa persona y muchos no tienen
ese archivo. Es una decisión de diseño: se toma a conciencia y se deja
escrita en un comentario del propio hook.

### Cuidados

- Un hook es un programa que corre en tu computadora, con tus permisos
  de usuario, en cada acción del agente. Uno que te pasa otra persona se
  lee entero antes de activarlo.
- Un hook lento se nota en cada acción: conviene que sea simple y
  rápido.
- Los hooks complementan los permisos, no los reemplazan: lo que se
  puede expresar como una regla `deny` se escribe como regla.
- El comando `/hooks`, dentro de una sesión, muestra los hooks activos.

## Cuándo usarlo

Cuando una regla tiene que cumplirse siempre y necesita lógica que un
permiso no puede expresar: validar datos, formatear después de editar,
bloquear un comando según sus argumentos.

## Buenas prácticas

- Reglas positivas en lugar de listas de prohibidos.
- Un mensaje de bloqueo que le diga al agente qué hacer en su lugar.
- Decidir y documentar si falla abierto o cerrado.
- Hooks simples, rápidos y revisados antes de activarlos.

## Anti-patrones

- **Confiar en una instrucción** para algo que tiene que cumplirse
  siempre.
- **Un hook que bloquea sin explicar** qué hacer.
- **Activar hooks ajenos** sin leerlos.
