Un asistente escribe código que parece correcto con mucha facilidad. Esta entrada muestra las preguntas con las que se revisa lo que produce, y cómo tratar su explicación de un fallo: como una hipótesis.

## Conceptos

### Lo que produce es un borrador

Todo lo que escribe un asistente (un test, un Page Object, la explicación
de un fallo) se trata como el Pull Request de una persona que no conoce
el proyecto: puede estar bien, y hay que comprobarlo antes de integrarlo.
Quien lo integra es responsable de ese código, no la herramienta que lo
escribió.

Las preguntas de esta entrada son las que se le hacen a cualquier test.
Lo que cambia es dónde mirar con más cuidado, porque un asistente no se
equivoca como una persona: rara vez escribe mal la sintaxis, y con más
frecuencia inventa lo que no conoce (entrada de cómo funciona un
asistente), verifica algo distinto de lo que promete, o ignora las reglas
de la suite, que no conoce si nadie se las dio.

Como ejemplo, el asistente escribió este test para la agenda:

```ts
test('cancelar un turno lo libera', async ({ page }) => {
  await page.goto('https://agenda-staging.clinica.test/agenda?fecha=2026-11-14');
  await page.getByRole('button', { name: 'Cancelar turno' }).first().click();
  await page.getByRole('button', { name: 'Confirmar' }).click();
  await page.waitForTimeout(2000);
  await expect(page.getByText('Turno cancelado')).toBeVisible();
});
```

Pasa. Las preguntas que siguen muestran por qué igual no se integra así.

### ¿Corre, y corre siempre?

Lo primero es ejecutarlo. Y no una vez: un test que depende de una espera
fija, como el `waitForTimeout(2000)` del ejemplo, puede pasar hoy y fallar
mañana, cuando la aplicación tarde un poco más. Con
`npx playwright test --repeat-each=20 --retries=0` se corre veinte veces
seguidas, sin reintentos que escondan los fallos (entrada de tests
inestables): si falla alguna, no es estable.

### ¿Puede fallar?

Un test que pasa no prueba nada si no puede fallar. La comprobación es
romper a propósito lo que verifica: cambiar el valor esperado por uno
imposible y correrlo.

```ts
await expect(agendaPage.estado('09:30')).toHaveText('Estado imposible');
```

Si con un valor imposible el test sigue pasando, la assertion no está
verificando: por ejemplo, porque apunta a otro elemento, o porque le
falta el `await` y Playwright nunca espera su resultado (entrada de
anatomía de un test).

### ¿Verifica lo que promete?

El título dice qué comprueba el test, y las assertions tienen que
comprobar exactamente eso. Un asistente tiende a verificar lo que se ve
fácil en la pantalla, aunque no sea el resultado del caso. En el ejemplo,
el título promete que el turno queda libre, y lo único que se verifica es
el mensaje «Turno cancelado». Si la aplicación muestra el mensaje y deja
el turno reservado, el test pasa igual. La assertion que corresponde es
sobre el estado del turno:

```ts
await expect(agendaPage.estado('09:30')).toHaveText('Libre');
```

### ¿Respeta el framework?

El código generado tiende a lo genérico, y el ejemplo lo muestra:

- usa `page` directamente, en lugar de `AgendaPage`: los locators tienen
  que estar en el Page Object (sección III);
- abre una dirección completa de staging: la página se abre con
  `agendaPage.abrir()`, que usa la `baseURL` del entorno donde corre;
- toma el primer botón con `.first()`: puede cancelar otro turno que el
  que creó el test;
- no crea su propio turno: depende de que exista uno en el entorno, en
  lugar de crearlo con una fixture;
- espera con `waitForTimeout`: las assertions de Playwright ya esperan
  solas hasta que se cumplen;
- no tiene pasos numerados con `test.step` ni los tags del equipo.

Funciona hoy y le cuesta mantenimiento al equipo mañana. La forma más
barata de evitarlo es que el asistente conozca las reglas desde el
principio (entrada de instrucciones del proyecto).

### ¿Existe todo lo que usa?

Las alucinaciones aparecen como métodos, assertions u opciones que no
existen. TypeScript las detecta sin correr el test:

```ts
await expect(agendaPage.estado('09:30')).toBeShown();
```

```text
error TS2339: Property 'toBeShown' does not exist on type 'MakeMatchers<void, Locator, {}>'.
```

Por eso conviene correr `npx tsc --noEmit` sobre el código generado, y
desconfiar de una opción que no conocés hasta encontrarla en la
documentación de la versión de Playwright del proyecto.

### La explicación de un fallo es una hipótesis

Cuando un asistente explica por qué falló un test, propone una causa.
Antes de aplicar el cambio que sugiere, la pregunta es la del triage
(entrada de tests inestables): ¿el test está mal, o la aplicación hace
algo que no debería?

El test de cancelar falla buscando el botón «Cancelar», y el asistente,
mirando el snapshot de la página, propone cambiar el locator a «Cancelar
turno». Si el diseño aprobado dice «Cancelar turno», el cambio es
correcto. Si dice «Cancelar», la aplicación tiene un defecto y el test no
se toca. El asistente no tiene cómo saberlo: el diseño aprobado no está
en su contexto.

## Cuándo usarlo

Con cada test, Page Object, fixture o explicación que produzca un
asistente, antes de integrarlo.

## Buenas prácticas

- Correr el código generado varias veces, sin reintentos.
- Romper a propósito el valor esperado y confirmar que el test falla.
- Comparar el título con lo que verifican las assertions.
- Pasar `npx tsc --noEmit` antes de correr.

## Anti-patrones

- **Integrar un test porque pasó a la primera.**
- **Aplicar la explicación de un fallo** sin preguntar si la aplicación
  está bien.
- **Aceptar código fuera del framework** porque «funciona».
