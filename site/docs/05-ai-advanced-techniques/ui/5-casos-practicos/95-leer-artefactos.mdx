Antes de pedirle a un agente que diagnostique o repare, hay que mirar qué hizo la aplicación, no suponer qué falló. Esta entrada se apoya en los traces de la sección II y los reportes de la sección III, y muestra el orden de trabajo, qué responde cada artefacto y cómo descartar primero lo sistémico.

## Conceptos

### La regla que más tiempo ahorra

Un test falla con «elemento no encontrado». Parece un locator roto. Puede
serlo, o puede ser que un paso anterior haya enviado el formulario solo y
la página ya no esté donde el test creía. El mensaje de error dice qué
línea del test falló; los **artefactos** de la ejecución dicen qué hizo
la aplicación. En CI se llama así a los archivos que guarda una
ejecución para mirarlos después: la captura, el trace, el video y los
reportes, que el workflow sube y se bajan desde la pestaña Actions
(entrada de CI con GitHub Actions). Es la misma palabra que en un
pipeline de agentes, con el mismo sentido: un archivo que deja un paso
para que lo use otro. La regla, para personas y para agentes:
**leer el artefacto antes de formar una teoría**.

Es una regla que aparece en los pedidos de los agentes de reparación y de
diagnóstico, porque es fácil saltearla con apuro.

### El orden de trabajo

1. **Abrir el artefacto**: la captura, el trace, el reporte (entradas de
   leer un fallo y de debugging).
2. **Leer qué se mergeó**: en una corrida de un Pull Request, su diff; en
   la nocturna, lo que el análisis atribuyó a cada grupo (entrada del
   router de causa raíz).
3. **Recién entonces formar una teoría**, y probarla reproduciendo, no
   razonando.

Tres reglas que cuestan un día cada vez que se rompen:

- **Nunca se declara una causa sin verificarla contra la aplicación
  corriendo.**
- **Un test que falla porque la aplicación cambió no es inestable**: se
  dice «la aplicación cambió» y se actualiza el test al comportamiento
  nuevo, o se reporta el defecto.
- **Un test que pasa solo no prueba que pase en la suite**: se valida
  junto a los demás antes de darlo por sano (entrada de paralelismo).

### Qué responde cada artefacto

- **La captura**: ¿en qué pantalla estaba la aplicación? Muchas veces es
  toda la pregunta. Si el test falla buscando un botón y la captura muestra
  otra pantalla, la navegación se desvió: el locator no es el problema.
- **El snapshot de accesibilidad**: ¿el elemento no estaba, o estaba con
  otro nombre? Sirve para probar un locator candidato contra el estado
  real del fallo antes de escribirlo (entrada de revisar lo que produce la
  IA).
- **El trace**: la corrida paso a paso, con el estado de la página en cada
  acción y los pedidos de red (entrada de debugging).
- **El video**: lo que ninguna otra cosa muestra, como la aplicación
  siguiendo adelante mientras el test todavía esperaba otra cosa. Se miran
  los segundos **antes** del fallo.
- **El resumen de la corrida**: los tests que fallaron y pasaron en un
  reintento cuentan como inestables, no como fallidos. Para el triage se
  usan esos conteos.

Un reporte de Allure no se abre con doble clic sobre el archivo: hay que
servirlo con un pequeño servidor web, con `npx allure open` (entrada de
reportes). El de Playwright se abre con
`npx playwright show-report` (entrada de leer un fallo).

### Primero, ¿es sistémico?

Un fallo es **sistémico** cuando no es de un test en particular sino de
algo que comparten todos: el entorno, la configuración, el ingreso. La
mayoría de las veces que fallan muchos tests a la vez, comparten una
sola causa.
Confirmarlo primero ahorra horas de arreglar tests uno por uno:

| Señal | Significado |
| :- | :- |
| Conexión rechazada o tiempo agotado al abrir la aplicación | El entorno está caído |
| La aplicación abre, pero todo ingreso falla | Se apunta al entorno equivocado |
| Todo falla en el mismo punto de la fixture de ingreso | El ingreso está roto: es un solo problema |
| Fallan todos los tests de una fixture y los demás pasan | La fixture compartida está rota |
| Errores distintos en tests distintos | Trabajo real, test por test |

El test de ingreso funciona como el canario de las minas, que avisaba
del gas antes que nadie: si falla, todo lo demás va a fallar. Correrlo
primero, solo, ahorra correr cuarenta tests para descubrir lo mismo.

### Test por test

Descartado lo sistémico, cada fallo según su síntoma:

- **El locator no encuentra el elemento**: posible locator desactualizado.
  Se confirma contra la aplicación y se corrige el locator.
- **Un valor o un contenido distinto del esperado**: la aplicación cambió,
  o es un defecto. Se lee el diff.
- **Un tiempo agotado en una acción que no depende del servidor**, como
  abrir un menú o un diálogo que la página ya tiene cargado: no es un
  entorno lento, es un defecto.
- **Pasó en un reintento**: inestable. Se anota y se investiga; no se
  silencia (entrada de tests inestables).

### Cuándo escalar en lugar de arreglar

- Muchos grupos de fallos sin relación y sin un Pull Request en común,
  el mismo caso que frena la válvula de seguridad: es una conversación
  con desarrollo, no una tarde de arreglar tests.
- Una corrección que tocaría código de la aplicación más allá de un
  atributo de test: se le pide al equipo en el Pull Request de la
  funcionalidad.
- Un escenario que el entorno no puede ejercitar: se documenta como una
  falta de cobertura, en lugar de escribir un test que aparenta cubrirlo.

## Cuándo usarlo

Ante cualquier rojo, propio o de un agente, y en los pedidos de los
agentes de diagnóstico y reparación, como su primera instrucción.

## Buenas prácticas

- Abrir el artefacto antes de leer el código del test.
- Descartar lo sistémico antes de ir test por test.
- Verificar cada causa contra la aplicación corriendo.

## Anti-patrones

- **Teorizar a partir del mensaje de error** solamente.
- **Arreglar cuarenta tests** cuando el ingreso está caído.
- **Llamar «inestable»** a un test que falla porque la aplicación cambió.
