Casi todos los tests de una aplicación con ingreso empiezan igual: ingresar. Esta entrada muestra cómo ingresar una sola vez por corrida, guardar la sesión y que cada test arranque ya ingresado, y cómo darles otra sesión, o ninguna, a los tests que lo necesitan.

## Conceptos

### El problema: ingresar en cada test

Casi todas las pantallas de la biblioteca exigen una sesión iniciada.
Cada test arranca con un contexto nuevo, sin cookies (entrada de hooks y
aislamiento), así que cada uno tendría que ingresar antes de probar lo
suyo. Una fixture o un `beforeEach` que ingresa por la interfaz resuelve
la repetición de código, pero no la de tiempo: con cuatrocientos tests,
son cuatrocientos ingresos que no verifican nada nuevo. Y si la pantalla
de ingreso falla, fallan los cuatrocientos.

### Guardar la sesión: `storageState`

Lo que hace que la aplicación reconozca a una persona como ingresada se
guarda en el navegador: cookies y almacenamiento local. Playwright puede
copiar ese estado a un archivo y cargarlo en otro contexto:

```ts
await page.context().storageState({ path: 'playwright/.auth/socia.json' });
```

El archivo es un JSON con las cookies y el almacenamiento de cada sitio.
Después de ingresar en la biblioteca:

```json
{
  "cookies": [
    {
      "name": "sesion",
      "value": "lucia",
      "domain": "localhost",
      "path": "/",
      "expires": -1,
      "httpOnly": false,
      "secure": false,
      "sameSite": "Lax"
    }
  ],
  "origins": []
}
```

Un contexto que se crea con ese estado ya tiene la cookie: la aplicación
lo trata como ingresado, sin pasar por el formulario. Por eso el archivo
es tan sensible como una contraseña: la carpeta `playwright/.auth/` va en
`.gitignore` (entrada de instalación).

### Ingresar una vez: el proyecto de setup

Playwright recomienda ingresar en un **proyecto de setup**: un archivo
que corre antes que los tests, ingresa una vez y guarda la sesión.

```ts
// tests/auth.setup.ts
import { test as setup, expect } from '@playwright/test';
import { variable } from '../helpers/entorno';

const archivoSesion = 'playwright/.auth/socia.json';

setup('ingresar con la socia de prueba', async ({ page }) => {
  await page.goto('/ingresar');
  await page.getByLabel('Email').fill(variable('SOCIA_EMAIL'));
  await page.getByLabel('Contraseña').fill(variable('SOCIA_CLAVE'));
  await page.getByRole('button', { name: 'Ingresar' }).click();
  await expect(page.getByRole('heading', { name: 'Mis préstamos' })).toBeVisible();
  await page.context().storageState({ path: archivoSesion });
});
```

Es un test como cualquier otro (`setup` es solo `test` con otro nombre),
que termina guardando el estado. La assertion antes de guardar es
importante: confirma que el ingreso funcionó, para no guardar una sesión
inválida que haga fallar a todos los tests con un error confuso.

En la configuración, dos proyectos:

```ts
projects: [
  { name: 'setup', testMatch: /.*\.setup\.ts/ },
  {
    name: 'chromium',
    use: { ...devices['Desktop Chrome'], storageState: 'playwright/.auth/socia.json' },
    dependencies: ['setup'],
  },
],
```

- El proyecto `setup` corre solo los archivos que terminan en `.setup.ts`
  (`testMatch` es una expresión regular).
- `storageState` en el `use` de `chromium` hace que cada test arranque con
  esa sesión.
- `dependencies: ['setup']` hace que `chromium` espere a que `setup`
  termine bien antes de empezar.

### Cómo se ve al correr

Aunque se pida un solo proyecto, su dependencia corre antes:

```bash
npx playwright test prestamos --project=chromium
```

```text
Running 2 tests using 1 worker
  ✓  1 [setup] › tests/auth.setup.ts:6:6 › ingresar con la socia de prueba (264ms)
  ✓  2 [chromium] › tests/prestamos.spec.ts:5:7 › Préstamos › renovar un préstamo extiende el vencimiento 14 días @smoke (163ms)
  2 passed (1.2s)
```

El ingreso corre una vez por corrida, no una vez por test. Si el setup
falla, los tests de `chromium` no corren: un solo error claro en lugar de
cientos.

`--no-deps` saltea las dependencias. Sirve para repetir un test rápido
cuando la sesión guardada sigue siendo válida; si el archivo no existe,
el error lo dice:

```text
Error: Error reading storage state from playwright/.auth/socia.json:
ENOENT: no such file or directory, open 'playwright/.auth/socia.json'
```

### Tests que necesitan otra sesión, o ninguna

Los tests del propio ingreso no pueden arrancar ingresados: necesitan un
contexto vacío. `test.use` reemplaza el estado para un archivo o un grupo:

```ts
test.use({ storageState: { cookies: [], origins: [] } });
```

Si la aplicación tiene roles distintos (una socia y una bibliotecaria),
el setup guarda un archivo por rol (`socia.json`, `bibliotecaria.json`), y
cada grupo de tests elige el suyo con `test.use({ storageState: '...' })`.

### Cuándo no hace falta

Si la aplicación no tiene ingreso, o si ingresar es una llamada barata a la
API, la infraestructura de setup no ahorra nada. Y si la sesión vence en
pocos minutos, una corrida larga puede quedarse con una sesión vencida a
mitad de camino: hay que conocer cuánto dura antes de reutilizarla.

## Cuándo usarlo

En toda suite cuya aplicación exige ingresar y que tiene más que un
puñado de tests. Los tests del ingreso, y los de cada rol, eligen su
estado con `test.use`.

## Buenas prácticas

- Ingresar una vez en un proyecto de setup, con dependencia en los
  proyectos de tests.
- Verificar que el ingreso funcionó antes de guardar la sesión.
- Mantener `playwright/.auth/` fuera del repositorio.
- Un archivo de sesión por rol.

## Anti-patrones

- **Ingresar por la interfaz en cada test** de una suite grande.
- **Versionar los archivos de sesión.**
- **Usar la sesión guardada en los tests del ingreso.**
- **Reutilizar una sesión** sin saber cuánto tarda en vencer.
