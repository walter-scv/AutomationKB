Anatomía de un test

Vas a tomar un caso de prueba que ya sabés ejecutar a mano, comprar una unidad de un activo, y ver cómo se convierte en un test automatizado claro, estable y fácil de diagnosticar cuando falla.

Al terminar vas a poder:
  • Traducir un caso manual a un test con la estructura Arrange, Act, Assert.
  • Escribir asserts que no se rompan cuando cambian los datos.
  • Usar test.step, tags y el matcher correcto según el dato.
  • Leer un error de Playwright y saber qué pasó.

Unos 20 minutos. Las actividades se guardan en tu navegador.

1El escenario: comprar una unidad

Todos los ejemplos de la knowledge base usan "Show me the money!", una app de inversiones. A la izquierda tiene la caja de ahorro con tu saldo, los activos que ya tenés (Mi portfolio) y los que podés comprar (Inversiones disponibles). Al elegir un activo, el panel principal muestra su detalle y te deja comprar o vender.

Si tuvieras que probar la compra a mano, tu caso de prueba sería este:

  1. Entrar a la app.
  2. En Mi portfolio, seleccionar Ternium Argentina.
  3. Anotar cuántas unidades tenés en "Cantidad adquirida".
  4. Escribir 1 en el campo Comprar.
  5. Hacer click en Realizar compra y esperar a que termine la operación.
  6. Resultado esperado: la cantidad adquirida es la que anotaste más 1.

Probalo en esta versión simplificada de la app. Fijate que el paso 3 es clave: sin anotar el valor de antes, no tenés contra qué comparar el de después.

2Quién habla con la pantalla: la Page Object

Un test no busca botones ni lee textos por su cuenta. Todo lo que tiene que ver con la pantalla vive en una clase llamada Page Object. Para esta pantalla es PortfolioPage, en project/pages/PortfolioPage.ts.

La Page Object ofrece dos tipos de cosas. Los locators le dicen a Playwright cómo encontrar un elemento, por ejemplo el botón de Ternium. Los métodos hacen una acción completa o leen un dato y lo devuelven listo para usar: getUnitsOwned() lee el texto "Cantidad adquirida: 10 unidades" y te devuelve el número 10.

Así el test queda corto y legible, y si mañana cambia la pantalla, se corrige un solo lugar. Cambiá la app de arriba al modo Ver qué hay detrás y hacé click en los elementos marcados para ver qué parte de PortfolioPage los maneja.

3Arrange, Act, Assert

Un test automatizado tiene las mismas tres partes que tu caso manual, conocidas como AAA:

  • Arrange (preparar): todo lo necesario para poder hacer la acción. En el caso manual, los pasos 1 a 3. Anotar las unidades de antes también es preparación: es el punto de partida contra el que vas a comparar.
  • Act (actuar): la acción que querés probar. Pasos 4 y 5: la compra.
  • Assert (verificar): comparar el resultado con lo esperado. Paso 6.

Si un test no se puede dividir así de limpio, casi siempre está probando más de una cosa y conviene separarlo en dos.

    4Qué hace bueno a un assert

    El assert es la verificación: expect(valorReal).toBe(valorEsperado). Si no coinciden, el test falla. Que exista no alcanza; tiene que estar bien armado. Estas tres reglas son las que vas a aplicar en las próximas actividades.

    Regla 1. El test no toca la pantalla directamente. Si necesitás un dato de la pantalla, se lo pedís a la Page Object. Si el test busca elementos por su cuenta, el día que cambie la pantalla hay que arreglar cada test en lugar de un solo lugar.

    Regla 2. El test no calcula. Sacar palabras de un texto, convertirlo a número o sumar montos es trabajo de la Page Object. El test solo compara.

    Regla 3. Se compara contra un valor calculado, nunca contra un número fijo. Si hoy tenés 10 unidades y escribís toBe(11), el test pasa una vez. Mañana, con 11 unidades, falla aunque la app funcione bien. Por eso se lee unitsBefore antes de comprar y se compara contra unitsBefore + 1.

    Así no
    const texto = await page.locator('p', { hasText: 'Cantidad adquirida' }).textContent();
const unidades = parseInt(texto.replace('Cantidad adquirida: ', ''));
expect(unidades).toBe(11);
    Rompe las tres reglas: busca el elemento, parsea el texto y usa un número fijo.
    Así sí
    // antes de comprar
const unitsBefore = await portfolioPage.getUnitsOwned();
// después de comprar
expect(await portfolioPage.getUnitsOwned()).toBe(unitsBefore + 1);
    La Page Object busca y convierte; el test solo compara contra el punto de partida.

      5Lo que agrega una suite real
      
  
      
    
      El test que corregiste funciona, pero en el proyecto real cada test lleva tres cosas más. Así se ven:
      
  
      
  
      test.describe('Portfolio @portfolio', () => {                         // (a) grupo con tag de feature
  test('buy asset increases units @smoke @p0 @portfolio', async ({ page }) => {   // (b) título + tags
    const portfolioPage = new PortfolioPage(page);

    await test.step('1- User navigates to the app', async () => {      // (c) paso con nombre
      await portfolioPage.navigate();
    });
    // ...
  });
});
      
  
      
    
      QuéPara qué sirve
      
    
      
      (a) test.describe con @portfolioAgrupa todos los tests de una pantalla. El tag @portfolio permite correr solo esos tests: npx playwright test --grep @portfolio.
      
      
      (b) Título + tagsEl título es una oración que dice qué verifica. Los tags indican importancia: @smoke se corre en cada cambio, @p0 es prioridad máxima.
      
      
      (c) test.step('N- ...')Envuelve cada paso con un nombre numerado. Si el test falla, el reporte dice "falló en el paso 4" en lugar de mostrar solo una línea de código.
      
          
  
      
  
      
    
      Y un detalle sobre los matchers, la función que compara después de expect. toBe() exige igualdad exacta, perfecto para contar unidades. Pero el saldo tiene decimales, y las computadoras redondean los decimales de forma imperfecta: 0.1 + 0.2 da 0.30000000000000004. Para montos se usa toBeCloseTo(valor, 2), que compara hasta 2 decimales.

        6Cómo leer un error de Playwright
        
  
        
    
        Cuando un test falla en la terminal, Playwright muestra siempre la misma estructura. Leerla en este orden te dice qué pasó sin abrir el código:
        
  
        
  
          
    
        1. La línea con ✘: qué test falló, en qué archivo y en qué navegador.
          2. 
    
        2. La línea Error: qué tipo de verificación falló, por ejemplo toBe. Si dice Timeout, el problema fue que no encontró un elemento a tiempo.
          3. 
    
        3. Expected y Received: lo que esperaba el test y lo que realmente devolvió la app. Si el test usaba un cálculo como unitsBefore + 1, acá ves el resultado ya calculado.
          4. 
    
        4. El fragmento de código: la línea marcada con > es la que falló, y las de alrededor muestran el contexto, incluido el test.step donde estaba.
